## Scope and review basis

This page summarizes Google's *Prepare and roll out a release* guide and linked Help Center guidance on testing, permission declarations, managed publishing, staged rollouts, and country targeting. Reviewed October 22, 2026. It describes Play Console operations, not a substitute for the Developer Program Policies or individual policies. Eligibility, target API rules, review state, and actual rollout state must be checked against current official guidance and the app's Console. For a quick check across store listings, reviewer access, rejection remediation, and release readiness, see App publishing readiness and best practices; this page expands on Play Console test tracks and release operations.

## Pre-release checks

Before creating a release, complete the store listing, App content review materials, pricing, and required Dashboard setup tasks. The user must have the permission for the selected track. Prepare review credentials, demo materials, and declarations. See Play Console Requirements and store listing best practices.

Play offers Open, Closed, and Internal testing tracks, plus Production. Internal testing supports up to 100 testers per app. Personal developer accounts created after November 13, 2023 must, before requesting production access, run a closed test with at least 12 testers continuously opted in for 14 days and complete the production-access questionnaire. Do not generalize this specific gate to Organization accounts or accounts created on other dates. See Google's [testing track guide](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en) and [new Personal account testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en).


### White-label and template-app account, listing, and review practices

The [February 10, 2025 white-label announcement](https://support.google.com/googleplay/android-developer/answer/15931448) has one direct body link. Its guide has 11 body text links and four example-image links, all itemized with access states in the announcement 11 child-link table. Its 30-item generic Help sidebar is tracked separately from body links. Treat the chain as four review areas:

- **Isolate account risk:** Google strongly recommends decentralized accounts per client or client group, either unmanaged by clients or managed with provider assistance. All apps in a central account display the same developer identity, and one app's policy issue may affect other apps in that account. Decentralized accounts are a strong recommendation, not a universal mandate; finance, health, VPN, and government services have separate Organization-account requirements. See Play Console Requirements.
- **Make each app meaningfully distinct:** Each template app should have a unique description, icon, graphics, and relevant screenshots. Explain real available functionality, regional differences, and intended users; screenshots should match the experience reviewers can reproduce. Avoid repeated copy, keyword stuffing, claims about unreleased features, or a brand-name-only swap. Pre-publish templates can improve filing consistency but still require per-app verification. See store listing best practices and Spam and Functionality.
- **Keep apps reviewable and usable:** Submit a complete, working app; check installation, launch, core flows, and third-party SDK behavior. Provide durable demo credentials, access steps, and review resources; never submit production-user credentials. Verify testing gates for the actual account type.
- **Manage review and launch:** Google recommends freezing code/content changes during review and monitoring Policy status. Processing may take hours to seven days or longer in exceptional cases; the Managed publishing help page recommends at least a one-week buffer and strongly recommends a closed test before using the feature for a product launch. It requires specified release/store permissions, applies to updates of already-published apps, and does not apply to first publication. It holds back most changes, with exceptions. White-label providers can also document recurring issues and fixes in a client release checklist.

Account decentralization, a review freeze, and Managed publishing are best-practice recommendations. Category eligibility, account data, accurate listings, app functionality, reviewer credentials, and applicable policies require case-by-case verification.

## Create and prepare a release

1. Create a release on the intended track. If an earlier release is outstanding, complete its rollout or remove/discard unpublished changes from Publishing overview first.
2. Upload an Android App Bundle. The official guide says legacy apps created before August 2021 may still use APKs for updates. Configure Play App Signing for the first release. A new app can change its initial app-signing key before a release is rolled out to Open testing or Production. After publication, use the dedicated Play Console key-upgrade process when eligible; do not confuse an upload-key reset with app-signing-key rotation. A key change/upgrade can affect existing testers, old builds, and API services that depend on certificate fingerprints. See [Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756?hl=en).
3. Check App bundle enhancements. Automatic protection requires Play App Signing and an AAB; advanced anti-tamper/device-check features are limited to selected partners. Verify eligibility and regression-test protected builds across tracks. This is optional protection, not a universal publication requirement. See [Automatic protection](https://support.google.com/googleplay/android-developer/answer/10183279?hl=en).
4. Enter a Play Console-only release name and localized, user-facing release notes. Release notes allow up to 500 Unicode characters per language and should describe the update rather than promote products or solicit user action. Configure translations before adding supported languages.
5. Inspect permissions in the AAB/APK. Play evaluates permissions during release; high-risk or sensitive permissions may require a Permissions Declaration Form and approval in App content. Minimize manifest/SDK permissions and match them to actual features. See the permissions declaration topic and sensitive permissions topic.

### Sensitive permissions can block publishing for the whole app

If any active track contains an app bundle with an undeclared restricted permission, Play Console may show an App content alert. Google's declaration guide says other app changes—including store presence, pricing, and distribution settings—may also be blocked until it is resolved. Complete the declaration and receive approval, or remove the permission and upload an appropriate build. The current guide says permission review may take several weeks. Publishing API release attempts can return an error when the permission has not been approved; the declaration/review may first need to be completed through the Play Console web UI.

Declarations generally ask for core functionality, permission use, review steps, a demo video, and access instructions for restricted content. Provide test-only credentials, never production-user credentials. If no special access is needed, say so accurately. Fields vary by permission/app; follow the current Console form.

## Review, managed publishing, and go-live timing

After preparing the draft, use Preview and confirm and resolve all errors. Errors block publication; warnings or minor issues may allow it. Whether the release publishes directly or enters the review queue depends on the change and Publishing overview state.

The [Publishing overview guide](https://support.google.com/googleplay/android-developer/answer/9859654?hl=en) distinguishes changes not sent for review, in review, and approved but ready to publish. Saving a change does not necessarily submit it: check Publishing overview and click **Send for review** when required. With Managed publishing enabled, most changes wait for the developer to publish after approval; the feature is unavailable for an app's first publication. Exceptions include increasing an existing staged rollout to 100%, updating release notes, or unpublishing. Google says processing may take hours to seven days or longer in exceptional cases and recommends at least a week of buffer between submission and go-live. This is planning advice, not a guaranteed review time.

### App, update, and item statuses: locate the publishing blocker

Google's [publishing-status guide](https://support.google.com/googleplay/android-developer/answer/9859751?hl=en) separates three levels: **App status** describes overall availability and audience; **Update status** describes the latest update; and **Item status** describes a specific component such as a release, content rating, or store-listing experiment. First identify the level that is blocked, then inspect Publishing overview or the relevant item. An item's state is not automatically the overall state of the app.

| Level | Representative statuses | Meaning and action |
| --- | --- | --- |
| App | Draft, Internal/Closed/Open testing, Pre-registration, Production | Shows whether the app is a draft, available on a testing track, in pre-registration, or available in Production. |
| App | No active releases, Unpublished | No current active rollout (for example, no release was rolled out or updates were rejected); or the developer unpublished the app. An unpublished app is not discoverable to new users, while existing users can still find it and updates are limited to them. |
| App | Removed by Google, Suspended by Google | Google removed or suspended the app. The guide says it is not discoverable; removal requires a compliant update to reinstate, while suspension requires a successful appeal. |
| Update | No pending changes, Changes not yet sent for review, In review, Previous | No pending submission, changes not submitted, under review, or a valid historical update. Changes in the not-sent section do not enter review automatically; click **Send for review** in Publishing overview when needed. |
| Update | Update rejected, App rejected | Both indicate noncompliance with policy or the DDA. **App rejected** is specific to a first-time publication while the app is still Draft. Fix and resubmit, or appeal when applicable. |
| Item | Draft, In review, Available, Previous, Update rejected/App rejected | Describes whether an individual item has been submitted, is under review, is currently available, was superseded, or was rejected with its update. |

For a first draft publication, expand and resolve blocking **Errors summary** items. Warnings or minor issues may still allow publication, but Google recommends addressing them. Standard publishing processes an approved update as soon as possible; Managed publishing applies to updates of existing apps and lets the developer choose when to publish after approval. Review can extend beyond seven days, so status descriptions are not fixed timeline guarantees.

The status article directly points to the [Developer Policy Center](https://play.google.com/developer-content-policy/) and [Developer Distribution Agreement](https://play.google.com/about/developer-distribution-agreement.html), the grounds for rejection; the [release preparation guide](https://support.google.com/googleplay/android-developer/answer/9859348?hl=en), [review and go-live controls](https://support.google.com/googleplay/android-developer/answer/9859654?hl=en), and [update or unpublish guide](https://support.google.com/googleplay/android-developer/answer/9859350?hl=en), for the operational steps; and [Play Console user permissions](https://support.google.com/googleplay/android-developer/answer/9844686?hl=en), for production, testing-track, tester, Play Games Services, and private-app permissions. Publishing overview and permission settings require account access. The [Play Academy launch course](https://playacademy.exceedlms.com/student/path/4914) is supplementary training, not a policy clause. The article's 29 related Help sidebar entries are a separate directory layer, listed in the app-review preparation topic.

### Submission activity: track each review submission

Google's [About your submission activity](https://support.google.com/googleplay/android-developer/answer/17118609?hl=en) records each group of changes sent for review as a unique submission. Its detail view contains a submission ID, source (Play Console or Publishing API), received time, status-update timestamps, and lifecycle status, helping identify exactly which changes were included and when they moved through review. Google says submission records are displayed starting **May 1, 2026**, with up to one year of history retained.

| Submission status | Official meaning and next step |
| --- | --- |
| In review | Google is evaluating the submission; the status remains until all necessary reviews are complete. |
| Ready to publish | The changes passed all reviews; publish manually when ready. |
| Published | The submission is live on Google Play. |
| Rejected | The changes did not comply with policy and were not published; for a rejected update, the last approved version remains live. |
| Cancelled | The submission was withdrawn. This can follow manual removal, replacement by a newer submission while the older one is in review, or the app being blocked/suspended. |

These are **per-submission workflow states**. They relate to, but are not the same as, the aggregate App, Update, and Item statuses above. One submission may contain several app changes, so first use its ID and source to identify the record, then compare the individual changes in Publishing overview. The latest rejected submission links to [Policy status](https://support.google.com/googleplay/android-developer/answer/9842754?hl=en) for the policy issue and remediation. The account-specific page and its direct children are inventoried in the enforcement and appeals topic.

### Pre-review checks: clear visible blockers before formal review

Google's [pre-review checks Help article](https://support.google.com/googleplay/android-developer/answer/14807773?hl=en) says Play Console runs automatic checks in the **Changes not yet sent for review** area of Publishing overview. That area appears only after changes have been made since the most recent review submission. Checks start automatically and show an estimated completion time. Developers can click **Send for review** before checks finish; Play completes the checks first. The current Help article says all checks finish within 15 minutes, usually faster.

Checks cover policy completeness and technical quality, including required App content declarations and app details, high crash rates on some devices or Android versions, and compatibility across Android versions. An issue may be fixable in Console, or may require code changes, a new build upload, or a developer-website update.

| Check result | Console handling | Review meaning |
| --- | --- | --- |
| Critical issue / mandatory check | Must be resolved before publication; examples include missing required App content declarations or app details. | This is not a soft warning that can be routinely bypassed. |
| Other deferrable issue | If Console permits, choose **Proceed anyway** and select a reason; sometimes confirm an external fix. The reason is logged in Activity log. If left unresolved, the issue can return in a later check. | The response itself does not determine the review outcome, but an unresolved issue can still cause rejection if the app is nonfunctional or violates quality requirements. |
| Checks still running | Submission can be initiated; checks continue and, if no critical issue is found, Play submits the changes for formal review after they complete. | This does not mean the checks were skipped or the app was approved. |

Pre-review checks are not the formal review and do not cover every formal-review question; passing them does not guarantee approval. The article says most checks run on the Play Console website, with only the near-instant subset available through the API. A user who can choose **Proceed anyway** needs at least one of these roles: production release, testing-track release, tester management, store-presence management, or Admin (all permissions). See [Play Console user permissions](https://support.google.com/googleplay/android-developer/answer/9844686?hl=en) for role details.

For updates, select a staged rollout percentage; a first Production release has no percentage option. Production country availability applies to current and future production releases. Open/Closed testing tracks follow production countries by default and can be unsynced when prerequisites are met; Internal testing is not country-restricted. Targeting follows the user's Play account country, not current GPS location. Adding a country for a paid app automatically adds a local price; subscription prices need separate review and setup. ### Production-access questionnaire and review

The application has three parts:

1. **About the closed test:** tester-recruitment difficulty; whether testers used all features; whether usage matched expected production behavior (and how it differed); and a summary of feedback and how it was collected.
2. **About the app/game:** target audience, value proposition, and estimated first-year installs. Google says these answers are not public and do not affect app visibility or eligibility for other developer programs.
3. **About production readiness:** changes made from test findings and how readiness for production was determined.

Click **Next** in each section to save; leaving or choosing Discard loses unsaved answers, and the final section requires **Apply**. Review usually takes seven days or less but can take longer; the account owner receives the result by email. Fewer than 12 opted-in testers or insufficient engagement may lead to a request for more closed testing. Before applying, independently check policy compliance, target audience/content ratings, stability, and working reviewer credentials; formal review is not a troubleshooting service.

### Closed-testing practices and the Play pre-launch report

The Help article recommends recruiting a diverse group representative of the intended audience; giving testers clear instructions and a feedback route; encouraging coverage of all app features; reviewing tester behavior and feedback; and fixing issues during the closed test. It requires continuous 14-day opt-in but does not specify a fixed daily-activity threshold or a universal numeric definition of “enough engagement.” Android testing guides recommend covering functionality, performance, accessibility, and device/API compatibility with a mix of local/unit, integration, and device-side tests. The [Play pre-launch report](https://support.google.com/googleplay/android-developer/answer/9842757) may run automatically after an AAB/APK upload or saving a Production release, subject to device-lab capacity. The [results guide](https://support.google.com/googleplay/android-developer/answer/9844487) explicitly says the report cannot guarantee finding every issue; it does not replace closed testing, manual acceptance, or regression on real devices.

### Play App Signing and Automatic protection: body summaries and key direct descendants

[Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756?hl=en) separates the developer-held upload key from the app signing key Google Play uses to sign final APKs. Keep both keys secure. If an upload key is lost, it can be reset through Play Console; enrolling also unlocks Play's App Bundle enhancements. The current page says new apps default to quantum-ready hybrid signing: Android 17/API 37 verifies the hybrid signature while older devices continue to use classical signatures. For OAuth, Maps, App Links, and similar services, register the actual app-signing certificate fingerprints shown in Play Console with API providers and `assetlinks.json`; do not register only the local upload key. Before rotating an app signing key, check every app sharing the signing identity, older Android behavior, and all services tied to certificate fingerprints.

If an app signing key is compromised or a stronger algorithm is needed, the current page allows an annual key upgrade for Android 17/API 37+ installs; API-provider fingerprints must then be updated. Enforce two-step verification for all Play Console users. A self-hosted Cloud KMS setup is a discouraged special case: it transfers signing operations and disaster-recovery responsibility to the developer and may make some Play enhancements unavailable.

[Automatic protection](https://support.google.com/googleplay/android-developer/answer/10183279?hl=en) can use an installer check to direct users who installed from unknown channels to Google Play. Automatic anti-tamper and device-check features are available only to selected partners. As reviewed, the article lists eligibility as monthly consumer spend of at least USD 25,000, or at least USD 20,000 in each of the previous six calendar months; or at least 1 million MAU in a sensitive app category; or participation in a Google Play program such as Play Pass. Eligibility can change and is surfaced through Console notifications. The feature requires Play App Signing, an AAB, and at least API 24. Basic protection works offline, but installer checks may need connectivity after the Play Store has been offline for a prolonged period. Device check requires anti-tamper and manages store-listing visibility on the developer's behalf. The article also documents incompatibility with App Bundle code transparency and that Internal App Sharing uploads are not protected. Test protected builds across tracks, including launch, performance, crashes, and native-to-Java callbacks. If an app depends on integrity protection, do not promote unprotected versions to open testing or Production. Anti-tamper protection cannot guarantee that all cracking is prevented.

## Release checklist

- [ ] App details, pricing, App content, review credentials/demo materials, package name, and target API are current.
- [ ] The right track is selected; if the new-Personal-account rule applies, complete the 12-tester/14-day closed test and production-access request.
- [ ] AAB, signing key, version code, mapping/debug symbols, release notes, and per-language character limits are checked.
- [ ] Remove unused test tracks and unnecessary permissions; obtain restricted-permission approval before the planned go-live date.
- [ ] Run Android Studio Play Policy Insights or the CI lint checks; verify each result against the official policy and any Play Console declaration.
- [ ] Submit required changes through Publishing overview and allow review time.
- [ ] Check markets, local prices, rollout percentage, and monitoring plan; expand rollout after reviewing stability.

### Stop a fully rolled-out release

Google's [Halting a fully rolled-out release](https://support.google.com/googleplay/android-developer/answer/16285429?hl=en) article says that after a serious issue, developers can halt a release rolled out to 100% of users on tracks other than Internal testing. This prevents new users from installing it and users not yet on that version from updating to it. If an eligible prior fully rolled-out version exists, Play makes that version available to new and eligible users. The release can later resume at a selected percentage after the issue is fixed.

Limits: you cannot halt the first release on a track, and a prior version with a policy violation cannot replace it. If the release has been live for a long time or most users already updated, halting may not remove the impact of copies already installed. Treat this as incident mitigation, not a guarantee that Play will force users already running the newer version to downgrade.

## 1. Start with the binding purpose limit

The [Play Integrity API Terms of Service](https://developer.android.com/google/play/integrity/terms) say the API is provided to protect app security and mitigate abuse, fraud, and unauthorized access. The [Google APIs Terms of Service](https://developers.google.com/terms) also apply. Developers **may not use Play Integrity API to fingerprint or track individual users or devices**. Feature eligibility and quotas can change. Google may remove features or reduce quota when an app or SDK no longer qualifies; approval for additional features or quota is limited to the specified app or SDK and does not automatically transfer with an app.

Technical guidance about app/device integrity, request validation, and risk tiers must therefore serve security and anti-abuse purposes. Verdicts, `requestHash`, `nonce`, Device Recall values, or combinations of them cannot be repurposed for cross-session identity resolution, advertising profiles, user/device tracking, or sensitive-trait inference. Device Recall has the same purpose restriction.

## 2. API processing and the developer’s Data safety response

The Terms page says the API always processes:

- App-provided request information, including `requestHash` and `nonce`;
- App metadata: package name, version, and signing certificate;
- Google Play license status for signed-in Play accounts on the device;
- A key attestation certificate and device attestation token generated by Google Play services.

Only when the app opts in to environment details does it additionally process app-activity information used to determine whether apps can capture the screen or control the device, and the device’s Google Play Protect status. The Terms page says data is encrypted, is not transferred to third parties, and is deleted after a fixed retention period. It does not publish the number of days, so this topic does not infer one.

The API’s data-handling statement **does not complete the app-level Data safety assessment for the developer**. Google says the developer is solely responsible for deciding how to answer the app’s Data safety form. Assess the API alongside the app, backend, and integrated SDK data flows. Do not infer that collection, sharing, security practices, or reporting duties for the entire app are automatically satisfied just because the API page describes encryption and deletion. See [Data safety](../data-safety/data-safety.en-US.md) and [User Data](../user-data/user-data.en-US.md).

## 3. Official integration guidance: validate, minimize, and respond in tiers

The [Play Integrity overview](https://developer.android.com/google/play/integrity/overview) recommends placing a request close to the protected action, considering Standard requests for most cases because of lower latency, and reserving more expensive Classic requests for infrequent, high-value or sensitive actions. Standard requests also require warming up a token provider as designed. Both paths require server-side decryption/verification and verdict checks before taking action.

Implementation practices include:

1. Bind the verdict to the current action. Standard uses `requestHash`; Classic uses a server-generated, unpredictable `nonce`. Include only the request fields needed for validation and check freshness/replay. Data in `requestHash` and `nonce` is visible in cleartext to the app and Google; hash or encrypt sensitive values first and do not pass them in plaintext.
2. Do not cache integrity verdicts. Fetch a fresh verdict near the protected request to reduce proxy/replay risk.
3. Check that `requestDetails` match the expected request, then check Play-recognized app integrity and license status before applying device-trust tiers.
4. Design graceful behavior below the highest trust tier. Higher device labels cover fewer devices, and a single strong-signal rejection can exclude legitimate users. Depending on risk, use multiple outcomes such as allow, allow with limits, additional verification/remediation, or deny.
5. Gather telemetry before strict enforcement, observe results across devices and distribution channels, and plan for service outages, error codes, and unavailable Play services. For suspicious high-risk actions, consider a challenge or additional verification instead of automatic rejection.

These are Android Developers implementation practices. They should not be rewritten as Play review policy clauses.

## 4. Standard, Classic, and server-side verification

| Path | Use | Core security checks |
| --- | --- | --- |
| [Standard request](https://developer.android.com/google/play/integrity/standard) | Most apps; prepare the provider in advance and request a token on demand before a server call. It typically responds faster. | Bind the current action digest with `requestHash`; send the token to the app backend; have the backend ask Google Play to decrypt/verify and match the verdict to the original request. Do not cache verdicts. |
| [Classic request](https://developer.android.com/google/play/integrity/classic) | Infrequent one-off checks for high-value or sensitive actions. Each fresh assessment costs more. | Generate a high-entropy, one-time `nonce` on the server and validate the nonce, request context, and freshness; account for replay/exfiltration risk and request quotas. |
| [Verdict format](https://developer.android.com/google/play/integrity/verdicts) | Standard and Classic return the same general JSON fields for request, account, app, device, and optional environment information. | After decoding, first verify `requestDetails` against the original request, then inspect verdicts. Do not take high-impact action solely on client-controlled values. |

An integration requires a [Google Cloud project and Console linking](https://developer.android.com/google/play/integrity/setup). The current setup page lists default daily request/decryption quotas, project-linking conditions, and differences for app versus SDK integrations. Check the live page during implementation because quotas, SDK versions, eligibility, and Console menus can change. This topic does not treat a current technical version number as a long-term policy deadline.

## 5. Device Recall: restricted purpose, retention, and sharing scope

[Device Recall](https://developer.android.com/google/play/integrity/device-recall) is a beta feature that requires approval. It stores up to three developer-defined values for a device. Developers can read and write only the limited values they associated with the device; the feature does not expose a device or user ID. Possible security uses include recording severe abuse, high-value reward redemption, or repeated abusive account creation.

- Use it only to protect app security and mitigate abuse, fraud, and unauthorized access. It also prohibits fingerprinting/tracking users or devices and storing sensitive characteristics such as gender, age, or location.
- Values are stored on Google servers. A verified token can be used for a write for up to 14 days; values are retained for three years after the last read or write. Developers can reset all three values for a device to `false` to clear them and reset timestamps.
- Apps in the same Play developer account share the three per-device values. After an app transfer, the app uses the new developer account’s data.
- Supported devices, Play Store/Play services, and a Play-licensed account are prerequisites. The feature is in beta; developers must submit the interest form and be approved.

Although these custom values are not user IDs, they are state associated with a device across reinstalls/resets. Restrict purpose and access, and assess the app’s own disclosure, retention, and user-rights duties. “No hardware ID is exposed” does not mean unrestricted tracking is allowed.

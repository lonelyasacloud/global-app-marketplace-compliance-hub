## Quick decision

- If an app is not the default SMS, Phone, or Assistant handler and does not qualify for a listed temporary exception, remove SMS and Call Log permissions from every published App Bundle/manifest.
- Even an eligible use must enable a critical core feature prominently documented in the store listing. The app would be broken or unusable without that feature. Declare the permissions in Play Console and obtain review approval.
- A default handler must be registered as the system default before requesting permission, and must stop accessing the data immediately after losing that role.
- Starting January 27, 2027, general account verification by phone call is no longer an allowed READ_CALL_LOG exception. Prefer the Digital Credentials API; use SMS Retriever or SMS User Consent for text verification, and assess Incoming Call Retriever's number-range matching for call verification.
- SMS, Call Log, and derived data must not be used for ads, cross-user profiling, sale, or purposes unrelated to the compliant core feature. Developers must not recreate restricted data through other permissions, APIs, or third-party sources.

## Permissions and core-functionality test

| Permission group | Example permissions named by the policy |
| --- | --- |
| SMS | READ_SMS, SEND_SMS, WRITE_SMS, RECEIVE_SMS, RECEIVE_WAP_PUSH, RECEIVE_MMS |
| Call Log | READ_CALL_LOG, WRITE_CALL_LOG, PROCESS_OUTGOING_CALLS |

Core functionality is the app's main purpose, which can consist of one or more features. Without it, the app is broken or unusable; the store listing must prominently describe and promote it. Permissions may only serve an approved core feature, not an undisclosed, unimplemented, or disallowed purpose. Google Play review and approval are separate requirements: technical access does not imply policy approval.

## Permitted default-handler uses

The app must be actively registered as the relevant system default handler before it prompts the user to accept permissions. It must immediately stop using them if it loses that status.

| Handler role | Permissions listed by the policy | Boundary |
| --- | --- | --- |
| Default SMS | READ_SMS, RECEIVE_MMS, RECEIVE_SMS, RECEIVE_WAP_PUSH, SEND_SMS, WRITE_SMS | Core SMS messaging experience. |
| Default Phone | SEND_SMS, PROCESS_OUTGOING_CALLS, READ_CALL_LOG, WRITE_CALL_LOG | Core calling/phone experience. |
| Default Assistant | READ_SMS, RECEIVE_MMS, RECEIVE_SMS, RECEIVE_WAP_PUSH, SEND_SMS, WRITE_SMS, READ_CALL_LOG | Core Assistant interaction, such as understanding and replying to texts in real time. |

For an active default handler, the policy allows contact prioritization using the same user's contact recency, frequency, or duration to surface important contacts or improve name recognition, when it enables that user's own initiated calls, texts, or actions. Data from one user must not directly influence another user's product experience. All listed uses remain subject to Play review and approval.

## Legacy APK exception

An exception may be requested for old APKs whose code can no longer be changed in the APK Exceptions field of the Permissions Declaration Form. All of these conditions apply:

1. Declare the specific APK/version codes.
2. The APK was published before January 1, 2019.
3. Serve a compliant alternative APK to users on Android Oreo (API 26) or higher.
4. The APKs requesting the exception represent only a very small, low-single-digit percentage of the install base.

Google Play reviews requests case by case. Unpublishing the noncompliant APK is another route. The exception field appears only in qualifying multi-APK configurations.

## Common disallowed use cases

The policy's examples are not exhaustive:

- Account or device authentication through broad SMS/Call Log access; content sharing or invitations.
- Contact prioritization when the app is not the default handler or system-level default contacts handler.
- Social-graph or personality profiling; call recording.
- Device performance boosters, storage/data management, family or device location.
- Smart/predictive keyboards; displaying SMS/calls in wallpapers, launchers, or other tools.
- SMS translation by a non-default handler; text-to-speech or speech-to-text outside an eligible role/exception.
- SMS/contact management outside an eligible default-handler or exception use.
- SMS/phone notification enhancement outside an eligible default-handler or exception use.
- Market research based on SMS; remote control of a user's phone or other devices.
- Selling SMS/Call Log data or monetizing/reselling it through SDKs.

Do not read full message or call histories for convenience when a safer alternative exists.

### Digital Credentials / TS.43 end-to-end implementation

The [Android phone-number verification guide](https://developer.android.com/identity/digital-credentials/phone-number-verification) (marked updated July 29, 2026) divides verification into a client credential request and a backend exchange. It supports Android 10/API 29 and later. Before implementation, establish a relationship with a carrier or aggregator, which usually provides a billable cloud API. The guide's sample listed `androidx.credentials` and `credentials-play-services-auth` `1.7.0-alpha03`; this is the example version on that page, not a current stable-version requirement. Recheck the dependency and carrier coverage before shipping.

| Step | Technical requirements and checks |
| --- | --- |
| 1. Request credential parameters on the backend | The backend requests a DCQL credential object from an aggregator and supplies a request ID and nonce. Use `number-verification/device-phone-number/ts43` to retrieve the device number, or `number-verification/verify/ts43` to verify an existing number. |
| 2. Create an OpenID4VP request on the backend | Place the aggregator credential object in `dcql_query`; use `openid4vp-v1-unsigned`, `response_type=vp_token`, and `response_mode=dc_api`. Generate a unique nonce for each request and make it match the nonce in the aggregator parameters. |
| 3. Request the credential through the client OS | Pass the backend-generated request to Credential Manager using `GetDigitalCredentialOption`. The user can cancel, and unsupported devices/SIMs can fail; keep manual entry or another verification fallback. |
| 4. Validate the response on the backend | Send the OpenID4VP response from the client to the backend. The guide calls for matching the request and credential nonces, confirming issuance by trusted Android Telephony, and checking issue time, expiry, and other validity properties. Confirm with the aggregator which side performs each validation. Errors can include malformed `invalid_request` and processing `server_error`. |
| 5. Exchange the credential for a number | Send the validated, encrypted TS.43 Digital Credential to the aggregator. The aggregator validates and decrypts it, then returns the verified number. |

#### `DigitalCredential` Java API reference → direct body links and key findings

The official Java API page (updated August 6, 2026) was readable. It defines `DigitalCredential` as a credential type generally used for verification/sign-in, but specifically warns that `credentialJson` **may contain a protocol error response and does not imply verification succeeded**. Parse it according to the protocol used in the request. A multi-credential request may return several `DigitalCredential` objects from one or more providers; check each one. System-infrastructure failures, provider crashes, and generic Credential Manager exceptions are non-protocol errors that abort the transaction without returning partial credentials. The constructor checks JSON validity only; valid JSON does not mean the credential or number was verified.

### Default SMS handler: delivery broadcasts, roles, and the historical KitKat guide

The [Telephony API](https://developer.android.com/reference/android/provider/Telephony)'s “Creating an SMS app” section directly links nine times to five unique targets: [`Telephony.Sms.Intents`](https://developer.android.com/reference/android/provider/Telephony.Sms.Intents), [`Manifest.permission`](https://developer.android.com/reference/android/Manifest.permission), [`Intent`](https://developer.android.com/reference/android/content/Intent), [`TelephonyManager`](https://developer.android.com/reference/android/telephony/TelephonyManager), and the 2013 [“Getting Your SMS Apps Ready for KitKat” guide](https://android-developers.googleblog.com/2013/10/getting-your-sms-apps-ready-for-kitkat.html). Its current API descriptions say:

- `SMS_DELIVER_ACTION` and `WAP_PUSH_DELIVER_ACTION` go only to the selected default SMS app; that app writes the received message to the SMS Provider and notifies the user. The corresponding receiver filters use `BROADCAST_SMS` and `BROADCAST_WAP_PUSH`.
- `SMS_RECEIVED_ACTION` is a notification broadcast to registered receivers; these observers are not expected to write the message or notify the user. The API says receiving it requires `RECEIVE_SMS`. This platform behavior does not make broad SMS access eligible under Play policy.
- The default SMS app also advertises `ACTION_SENDTO` for SMS/MMS schemes and a `RESPOND_VIA_MESSAGE` service. `ACTION_RESPOND_VIA_MESSAGE` carries the recipient in a `sms:`, `smsto:`, `mms:`, or `mmsto:` URI, and may contain message text/subject. The `SEND_RESPOND_VIA_MESSAGE` documentation is easy to misread: `Manifest.permission` says it is not for third-party applications, while `TelephonyManager` and the SMS-role sample place it in the service's `android:permission` attribute, which limits who can invoke that service. Do not add it as the app's own `<uses-permission>` or infer a Play permission exception from this platform service pattern.

The linked [2013 KitKat guide](https://android-developers.googleblog.com/2013/10/getting-your-sms-apps-ready-for-kitkat.html) has seven body-link occurrences and six unique API targets: `Intent.ACTION_SENDTO`, `TelephonyManager.ACTION_RESPOND_VIA_MESSAGE`, the shared `Manifest.permission` page, `PackageManager.setComponentEnabledSetting()`, `SmsManager`, and `Context.startActivity()`. The linked API pages were opened and the relevant members sampled. `SmsManager.sendTextMessage()` requires `SEND_SMS`; the current platform reference classifies `SEND_SMS` as dangerous and hard-restricted. Direct sending therefore has its own runtime/platform and Play eligibility checks; it is not a permission-free way to receive or inspect messages. `PackageManager.setComponentEnabledSetting()` can change whether a receiver is enabled, which the 2013 guide used for its Android 4.4 `SMS_RECEIVED_ACTION` example. Treat that advice as historical platform migration material, not current Play policy.

The historical guide also demonstrates `Telephony.Sms.Intents.ACTION_CHANGE_DEFAULT` to request the SMS role. The current API explicitly says that action has not been supported since Android Q and points to [`RoleManager`](https://developer.android.com/reference/android/app/role/RoleManager): check whether `ROLE_SMS` is available, then request it through the user-consent intent returned by `createRequestRoleIntent()`. The RoleManager page links to the [AndroidX Role package](https://developer.android.com/reference/androidx/core/role/package-summary) and its [`RoleManagerCompat`](https://developer.android.com/reference/androidx/core/role/RoleManagerCompat); the compatibility reference lists SMS-role manifest components and `Intent.CATEGORY_APP_MESSAGING`. Those components describe Android platform role qualification, not Play approval. Play still separately requires a qualifying core function, the applicable declaration, and review approval before restricted permissions are used.

### Phone Number Hint implementation path: a selected number is not a verified number

The SMS Retriever client guide mentions a hint picker to reduce manual entry, but its code sample uses the older `HintRequest` / `Auth.CredentialsApi.getHintPickerIntent` flow. The separate [current Phone Number Hint guide](https://developer.android.com/identity/phone-number-hint), updated October 21, 2026, uses `GetPhoneNumberHintIntentRequest`, `Identity.getSignInClient(activity)`, and `SignInClient.getPhoneNumberHintIntent()`. The user selects or cancels one of the SIM-based numbers available on the device; the app needs no extra permission or Google Account. Do not conflate the APIs in the two pages as one current implementation; check the dedicated current guide and project dependencies before implementation.

A number hint returns the number string selected by the user. It **does not prove control of that number or complete verification**. Use SMS Retriever, SMS User Consent, manual code entry, or another suitable verification flow to verify it; the server should generate and verify codes, limit their validity, and prevent reuse. If the app transmits, stores, or uses the number for other purposes, separately review User Data, Data safety, privacy disclosures, security, and consent duties. The system hint UI does not replace them.

The current guide's main flow is: create `GetPhoneNumberHintIntentRequest` → call `Identity.getSignInClient(activity).getPhoneNumberHintIntent(request)` to obtain a `PendingIntent` → launch it through an Activity Result flow → pass the result `Intent` to `getPhoneNumberFromIntent()`. The public `SignInClient` reference lists these two Phone Number Hint methods as available; the same page marks several traditional sign-in methods deprecated and recommends Credential Manager. Do not extend those deprecation markers to the Phone Number Hint methods.

### SMS User Consent direct pages and Smart Lock migration path

[SMS User Consent overview](https://developers.google.com/identity/sms-retriever/user-consent/overview) is a narrow fallback when SMS Retriever is unsuitable: if the app cannot control the verification-message format, the user can approve access to one SMS. After approval, the SDK gives the app the entire message, so parse only the code and avoid logging or retaining unrelated content. Keep manual entry if the user declines, the message reaches another device, or the flow times out. Start listening before the server sends the SMS; the guide's example uses a five-minute window and supports an optional sender-number filter. The code must still be verified by the server.

The overview links directly to the SMS Retriever overview and the [one-time SMS consent implementation guide](https://developers.google.com/identity/sms-retriever/user-consent/request). The latter describes matching a 4–10 character alphanumeric OTP containing at least one digit, with an optional sender filter. The page was last updated October 31, 2024 and its dependency examples are old; recheck current Google Play services/AndroidX dependencies for the project and do not treat those sample versions as Play requirements. If the app can control the SMS format, prefer SMS Retriever, which does not require SMS-read permission.

The implementation guide also links to the deprecated [Smart Lock password sign-in hints](https://developers.google.com/identity/smartlock-passwords/android/retrieve-hints), whose sign-in hint flow should migrate to [Credential Manager](https://developer.android.com/training/sign-in/passkeys/). ### Incoming Call Retriever: least-permission call verification

The [Incoming Call Retriever API reference](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetrieverClient) describes phone-number verification without broad `READ_CALL_LOG`: the app supplies an expected number range; after user consent, the API intercepts and rejects the first matching call within a limited time, then broadcasts the verification result. The interface requires Android 10 / API 29 or later. It may report `API_UNAVAILABLE` when telephony is unavailable, the device/SIM is unsupported, or the client is not authorized for the API.

Google's API reference explicitly requires an [Incoming Call Retriever access request form](https://docs.google.com/forms/d/e/1FAIpQLSezoJZPt6L-J-httaMiSJnHFUIF0oR1n0Xvvpoxco9LB42LMg/viewform). Reopened on October 23, 2026, the public form says access is restricted to valid use cases and requires a separate request for each app. Required fields include contact email, company/organization, a store link, exact package name, detailed use case and user journey, and supporting evidence such as an existing call-verification flow PDF or UI mock. The page was readable; no form was submitted. **API access is separate from a Play permissions declaration or policy exception, and an API request does not guarantee approval.** The API reference recommends Digital Credentials first and names Firebase Phone Number Verification as a provider route; SMS Retriever is an alternative for SMS OTP. Before choosing Incoming Call Retriever, confirm access eligibility and service coverage for the app.

| Step | Implementation and fallback |
| --- | --- |
| 1. Check device capability | Check whether `Context.TELEPHONY_SERVICE` is available before starting. The API is marked `@RequiresApi(29)`. If telephony, the applicable SIM, or the API is unavailable—or the client is unauthorized—use another verification route; do not fall back to broad `READ_CALL_LOG` without policy eligibility and approval. |
| 2. Request and display consent | Call `startIncomingCallRetriever(request)` to begin verification and request consent when needed, or call `startUserConsent()` first. The successful `Task<PendingIntent>` is launched from an Activity to display the system consent UI. Proceed only after consent is granted or a recent consent is explicitly treated as success. |
| 3. Match a verification call | The request object constrains the number range that the backend may use for the verification call. After consent, the backend must call within the API's time window from a number matching that range. The API rejects only the first matching call and sends a status broadcast for success, failure, or timeout. This is not general call screening, Call Log access, or a way to read arbitrary numbers. |
| 4. Handle results | Check the Activity `requestCode` before processing the `resultCode` and status code. Denial, cancellation, and rate limiting should stop verification and offer another route. Handle `ApiException` and other `Exception` values asynchronously; specifically handle `IncomingCallRetrieverStatusCodes.API_UNAVAILABLE`. |
| 5. Protect the result receiver | Register a `BroadcastReceiver` in the manifest, filter `PHONE_VERIFICATION_STATUS_INTENT_ACTION`, and set `android:permission` to `com.google.android.gms.auth.api.phone.permission.SEND` so only Google Play services can send the result broadcast. **Do not** add this permission as an app `<uses-permission>`. The reference recommends a statically registered receiver so the result can arrive when the app is not running. |

#### Grandchild API references: number range, consent result, and failure statuses

On October 24, 2026, I opened the [`IncomingCallRetrieverRequest`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetrieverRequest), [`IncomingCallRetriever`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetriever), and [`IncomingCallRetrieverStatusCodes`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetrieverStatusCodes) references. | API target | Constraints stated in the reference | Implementation implication / unresolved point |
| --- | --- | --- |
| [`IncomingCallRetrieverRequest`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetrieverRequest) | The request contains a country code (without `+`), phone-number prefix, inclusive `startRange`, and `endRange`. The prefix is required when the number after the country code has ten or more digits; the bounds must have equal digit counts and `startRange ≤ endRange`. The suffix of the expected incoming number must fall within that range. | Keep the server's calling-number pool and client range aligned; only expected verification calls should match. The page says the total number length should equal country-code digits + prefix digits + range digits, but its example also shows a shorter suffix (`12`) and bounds with leading zeros (`000000`), which appear in tension with the length statement. Do not infer variable-length or leading-zero matching rules from the example; confirm actual number formats with API support before release. |
| [`IncomingCallRetriever`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetriever) | Consent Activity results use `ACTIVITY_RESULT_INTENT_EXTRA_STATUS_CODE` and the explanatory `ACTIVITY_RESULT_INTENT_EXTRA_MESSAGE`; completed verification broadcasts use `PHONE_VERIFICATION_STATUS_INTENT_ACTION` and carry a result in `PHONE_VERIFICATION_STATUS_INTENT_EXTRA`. Calls that launch consent UI need an Activity context; an Application-only context fails when the API tries to start the UI. | `SUCCESS_CACHE` means recent consent may be reused; it does not mean a new consent dialog was just shown and accepted. | [`IncomingCallRetrieverStatusCodes`](https://developers.google.com/android/reference/com/google/android/gms/auth/api/phone/IncomingCallRetrieverStatusCodes) | The public constants include `CONCURRENT_REQUESTS`, `IN_EMERGENCY_CALL`, `API_UNAVAILABLE`, `RATE_LIMIT_REACHED`, `TELEPHONY_FEATURE_UNAVAILABLE`, `INVALID_PHONE_NUMBER_RANGE`, `USER_CONSENT_DENIED`, and `FAILURE_OTHER`. | These are public status values. The references give brief status descriptions (for example, `API_UNAVAILABLE` means the API is currently unavailable); the client page separately lists possible causes including unsupported device/API, unauthorized client, and missing SIM support. The enum names help classify failures, but the docs do not prescribe retry intervals or business handling for every code. The fallback suggestions above are implementation guidance, not official policy. The API references say they were last updated July 7, 2026; recheck them for the specific integration.

Relationship to the January 27, 2027 change: this is a narrow technical route for number verification, but it does not change Play's restricted-permission eligibility rules. Once the general phone-call account-verification exception expires, migrate to a route that does not read `READ_CALL_LOG`. Banking and brokerage call-based authentication is listed as a separate policy use case and must be assessed against its own eligibility, core-functionality, declaration, and review requirements.

## Play Console declaration and review

1. Check all uploaded App Bundles/APKs, including Open, Closed, and Internal testing tracks; align actual permissions with the declared use.
2. In App content, complete the Permissions Declaration Form, select a supported core use, and explain how the permission enables a core feature prominent in the store listing.
3. Provide review instructions and a video. For sign-in-gated features, provide a test-only account/number and access steps; never provide production-user credentials.
4. For a qualifying legacy APK exception, enter the version codes and deactivate noncompliant APKs or unused testing tracks.
5. Attest that the declaration is accurate. Resubmit an updated declaration if permission use changes.
6. Allow time for extended review. The official guide says processing may take several weeks. For an urgent release, remove high-risk permissions and submit a new release for standard review.

Missing declarations, disallowed uses, or inadequate evidence can block publication or lead to removal. Publishing API users still need to complete the initial declaration/review and declarations for new permissions through the Console workflow.

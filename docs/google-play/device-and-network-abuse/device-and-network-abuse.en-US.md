## Core prohibitions

The policy does not allow an app or its third-party SDKs to access, interfere with, disrupt, damage, or modify without authorization a user's device, other devices, servers, networks, APIs, services, other apps on the device, Google services, or an authorized carrier network. Key risks include:

- Modifying, replacing, or updating an app outside Google Play's update mechanism; downloading executable code (such as DEX, JAR, or `.so`) from outside Play. The policy preserves an exception for code running in a virtual machine or interpreter that indirectly accesses Android APIs; however, runtime-loaded interpreted code must not enable Play policy violations.
- Exploiting security vulnerabilities, facilitating hacking, making game cheats that affect other apps, or using an API/service in a way that violates its terms.
- Blocking another app's ads, installing other apps without prior user consent, facilitating malware distribution, or bypassing Android power management without eligibility.
- Providing proxy services to third parties unless the proxy itself is the app's primary user-facing core purpose.
- Loading untrusted pages or unverified URLs in a WebView with a JavaScript Interface; or using `FULL_SCREEN_INTENT` to force interaction with disruptive ads or notifications.
- Circumventing the Android sandbox to derive user activity or identity from other apps.

Android system optimization requirements should be read with [Core App Quality](https://developer.android.com/docs/quality-guidelines/core-app-quality) and platform power-management documentation. Remote content, interpreters, and SDKs are not automatically violations, but they must not introduce executable-code abuse, undisclosed behavior, vulnerabilities, or other policy violations. Developers remain responsible for code and SDK behavior included in their apps.

## Foreground services (FGS)

Apps targeting Android 14/API 34 or higher must declare the accurate manifest service type and matching permission for each FGS, and declare the actual use case in Play Console. An FGS use must support a user-beneficial feature related to the app's core functionality, be user-initiated or continuously perceptible, be stoppable by the user, be unsuitable for safe deferral/interruption, and run only as long as needed. The Play page lists `systemExempted`, `shortService`, and `dataSync` only when used for Play Asset Delivery as exceptions. This is not a blanket exemption for every service of those types.

The declaration must describe the feature, user impact if it is delayed/interrupted, and the use case, with a video showing how the user triggers it. Android type/permission/start rules and Play review are separate layers; a manifest declaration does not equal Play approval. See the bilingual FGS and geofencing topic (snapshot: `foreground-services-and-geofencing-en.md`, not imported in this repository) for the full workflow. Geofencing has a separate upcoming change effective January 27, 2027; check that topic and the policy deadline register (snapshot: `../google-play-policy-link-graph-en.md`, not imported in this repository).

## User-initiated data transfer (UIDT)

UIDT is a long-running network-transfer job type provided by `JobScheduler` starting in Android 14/API 34. It is not a Play permission or compliance exemption. All three substantive conditions should hold: the user explicitly initiated the transfer, the work actually uploads or downloads data over a network, and the user needs visible progress such that safe deferral or interruption would harm the experience. Automatic backup/sync, non-network work, short interruptible transfers, and persistent work whose purpose is merely to keep a process alive should not use UIDT to gain higher priority. Play's Device and Network Abuse and FGS rules remain separate; UIDT does not exempt downloads of executable code from outside Play or other policy restrictions.

### Choose an API and implementation checks

| Work characteristics | Prefer | Boundary |
| --- | --- | --- |
| Deferrable, short, interruptible, or automatically initiated sync | [WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent) | Better suited to constraints, retries, and scheduling that persists across restarts; consider expedited work only when prompt execution is needed. Long-running workers remain subject to FGS and system limits. |
| Long network upload/download explicitly started by the user, with visible progress required and harmful interruption | [UIDT `JobScheduler` job](https://developer.android.com/develop/background-work/background-tasks/uidt) | Android 14/API 34+; the app must be visible or satisfy an allowed background-launch condition when scheduling. That condition is not the same as an FGS background-start exemption. |
| Short, critical work expected to finish in about three minutes, when other scheduling APIs do not fit | FGS `shortService` or a suitable specific API | Android service-type/start rules and Play FGS declaration, user-benefit, stoppability, and review requirements must all be met separately; a visible notification alone is not sufficient. |
| A dedicated device or use-case API exists | Specific API | Prefer a purpose-built API with better system integration, such as a Companion Device route for local-device transfer; do not choose a generic background API solely because data is moving. |

Key UIDT implementation checks:

- Register a `JobService` protected by `android.permission.BIND_JOB_SERVICE`; declare `android.permission.RUN_USER_INITIATED_JOBS`; and call API-34 `setUserInitiated(true)` when building `JobInfo`. Handle `RESULT_FAILURE`, including when foreground/allowed scheduling conditions are not met.
- Provide the most accurate upload/download byte estimate possible with `setEstimatedNetworkBytes()`, and set network, charging, battery, and storage constraints as needed. Update estimates when they become known or change. Constraints help select an appropriate execution window, but system-health limits can still stop a job.
- Run the transfer asynchronously from `onStartJob()`, keep the user informed through `JobService.setNotification()`, and call `jobFinished()` promptly after either success or failure. Implement `onStopJob()` for system stops and recoverable state. Do not use `getStopReason()` for critical business logic; it is primarily for diagnostics and logging.
- A Task Manager stop immediately kills the entire app process, does not call `onStopJob()`, and prevents that user-visible job from being rescheduled. Provide appropriate stop/resume controls in the notification and persist resumable transfer checkpoints/state so a later app launch can safely restore progress.
- As of the UIDT guide's October 16, 2026 update, no Jetpack library supports UIDT. For API levels below 34, select a compatible alternative. If falling back to WorkManager's foreground-service implementation, Android FGS start rules and Play policy declaration still apply.

Google Maps' official case study reports a greater-than-10% improvement in offline-download failure rate after migrating from FGS to UIDT. This is one product's retrospective experiment, not a guaranteed result for every app and not Play approval of a particular use case.

## `FLAG_SECURE`

Apps must respect other apps' `FLAG_SECURE` declarations for sensitive UI and must not provide workarounds to capture protected content. An Accessibility Tool may use the stated exception only if it does not transmit, save, or cache protected content outside the device. The Android API reference is [WindowManager.LayoutParams](https://developer.android.com/reference/android/view/WindowManager.LayoutParams); the full rule and exception are in the Play policy above.

## On-device Android containers and `REQUIRE_SECURE_ENV`

An on-device Android container may load third-party APKs into its own app space and intercept or proxy APIs so that they appear to run in a normal Android environment. An app may declare `REQUIRE_SECURE_ENV` in its manifest to signal that it should not run inside such a container. The flag does not technically block loading; Play policy requires container apps distributed on Play to inspect the target manifest, not load apps with the flag, not proxy their calls, and not bypass the flag by loading an older version.

The Help FAQ clarifies that enterprise apps creating a separate work profile and requiring device-admin permissions are not treated as containers under this definition. Whether to declare the flag is up to the app developer's security and privacy needs. For container implementation, see [Limit loading in on-device Android containers](https://developer.android.com/training/basics/intents/limit-play-loading); this is technical guidance, not a substitute for Play policy.

The Android guide (last updated March 5, 2026) shows the flag under `<application>`:

```xml
<application>
    <property android:name="REQUIRE_SECURE_ENV" android:value="1" />
</application>
```

The use-case guide explicitly says the flag can be used regardless of the Android version on which the app runs. The generic [Manifest `<property>` reference](https://developer.android.com/guide/topics/manifest/property-element) labels this general element as introduced in API 31 and distinguishes an ordinary `android:value` from a resource ID in `android:resource`; it says the two should not both be set on one `<property>`. These statements address different layers. Do not turn the generic API-level label into a new Play minimum-version requirement for this flag, or describe the flag as an operating-system-enforced container block. It is a declaration by the app publisher that container operators must inspect and respect under Play policy.

This review followed the guide's direct targets and the relevant Manifest-reference descendants. ## Battery-optimization exemption: policy and implementation boundary

Play prohibits apps that are not eligible for allowlisting from bypassing system power management. The Android Doze guide further says apps on Android 6.0+ must not directly request to ignore battery optimizations when their core function would not be adversely affected. “Background work is important” alone does not establish eligibility. First check whether FCM `RemoteNotification`, deferrable/resumable work, or a purpose-built API can satisfy the core scenario. Only then document a real technical dependency that prevents FCM use or concrete damage to the core function from Doze/App Standby. Safety apps, core task-automation apps, and companion apps maintaining a persistent connection to provide internet access to a peripheral are listed as acceptable categories; periodic sync, standard Bluetooth-headphone use, and messaging scenarios that can use FCM are listed as not acceptable. These categories are not pre-approval of an individual app; see recursive graph section 4.71 for the full matrix and `Settings`/`PowerManager` explanation.

`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` opens system settings. `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` directly asks to add the app to the power allowlist and requires the corresponding manifest permission. `isIgnoringBatteryOptimizations()` only checks system allowlist state; it does not prove Play eligibility. An FGS is not a general way to keep a process alive or avoid idle classification.

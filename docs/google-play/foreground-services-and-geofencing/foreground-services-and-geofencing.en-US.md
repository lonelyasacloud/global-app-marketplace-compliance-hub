## Play policy: does the work actually need an FGS?

Except for limited policy exemptions, an FGS must meet these criteria:

- It supports a user-beneficial feature related to the app's core functionality.
- The user initiates it, or the work remains perceptible to the user—for example, active audio playback, a clear ongoing notification, or an upload the user requested.
- The user can stop it.
- Deferring or interrupting the task would harm the user experience or prevent the expected feature from working as intended.
- The service runs only as long as needed to finish the task, then stops.

A persistent notification alone does not establish that an FGS is appropriate. If the system can run the work later without harming the experience, prefer a background-work API such as WorkManager. Consider UIDT on Android 14+ only when the user explicitly initiated a network transfer, needs ongoing progress, and interruption would harm the experience. UIDT is an Android scheduling API, not Play approval or an FGS exemption; see the [Device and Network Abuse topic](../device-and-network-abuse/device-and-network-abuse.en-US.md). Each alternative has its own limits.

Current Play policy lists `systemExempted` and `shortService` types, plus `dataSync` only when using Play Asset Delivery, as exceptions to the general FGS criteria above. Android separately checks whether a service type can run on the system: the current Android type guide's `systemExempted` conditions include system apps, specific integrations, and VPN apps configured in system Settings; they also include holding `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM`, among other conditions. The system throws an exception when platform conditions are not met. This platform eligibility does not mean every app using `VpnService` automatically qualifies for a Play FGS-policy exception or Console approval. `shortService` is a roughly three-minute type that needs no type-specific permission but still needs the base `FOREGROUND_SERVICE` permission. `specialUse` is not a general bypass; its manifest subtype is reviewed in Play Console. The AOSP ToyVpn sample uses `specialUse` with subtype `vpn`; see the [dedicated topic](../vpnservice-policy-and-implementation/vpnservice-policy-and-implementation.en-US.md) and verify the type for the actual app. Play policy exceptions, Android type eligibility, and Play Console declarations are separate rules. Do not infer approval of a Console form from the system accepting a type. `USE_EXACT_ALARM` also has its own Play permission policy; see [Sensitive permissions and APIs](../sensitive-permissions/sensitive-permissions.en-US.md).

## Android 14+ declarations and the Play Console form

For apps targeting Android 14/API 34 or higher, declare the accurate `android:foregroundServiceType` for each service in the manifest, along with the base `FOREGROUND_SERVICE` permission and the permission for that type (for example, `FOREGROUND_SERVICE_LOCATION` for `location`). A service may also need separate runtime permissions for location, microphone, camera, or body sensors.

Apps targeting Android 14+ must also declare the FGS types they use in Play Console under **Monitor and improve → App content**. For every type, provide:

1. A description of the app functionality using that type.
2. The user impact if the system delays, interrupts, or restarts the task.
3. A video showing how the user triggers the feature in the app.
4. The most suitable use case. The preset list is not exhaustive; explain a use case if it is not listed.

The declared type must match the work the service really performs. Keep the declaration, video, advertised core feature, code, and SDK behavior consistent.

## Android start restrictions and location permission boundaries

- Starting with Android 12/API 31, starting an FGS from the background is generally restricted, subject to defined exemptions. Android 14/API 34 also checks while-in-use permissions when the service starts.
- An FGS that needs camera, microphone, location, or some body-sensor permissions generally must be started while the app has a visible activity. Specific system-defined exemptions and background permissions affect technical eligibility, but do not automatically waive Play policy review.
- Android's `checkSelfPermission()` can return `PERMISSION_GRANTED` for a while-in-use permission while the app is in the background. That only means the app has the permission while in use; it does not prove the FGS can be created at that moment. On Android 14+, creation can directly throw a `SecurityException`. Do not treat the permission-check result as permission to start from background.
- A `location` FGS requires Location Services to be enabled and coarse or fine location permission. Starting it from the background may also require `ACCESS_BACKGROUND_LOCATION`.
- If the service's behavior constitutes background location access, the [background location topic](../background-location/background-location.en-US.md) still applies: core-function necessity, minimum scope, prominent disclosure, and Play Console review. An FGS cannot be used to bypass Play's location rules.

Android's general background-start exemptions and while-in-use location access are separate platform conditions: meeting an FGS start exemption does not automatically meet the location-access condition for a background location FGS. Android documents background-start events such as alarms and geofencing separately from while-in-use restrictions and `ACCESS_BACKGROUND_LOCATION`. Play's FGS eligibility and location policy apply independently. In particular, Android lists a geofencing event as a background FGS-start case, while Play has announced that geofencing will no longer be an approved FGS use case on **2027-01-27**. The ability to start under Android's rule does not establish that Play allows that use.

An exact alarm is also only a conditional Android start exemption: the app must invoke it to complete an action requested by the user. This platform exception does not grant exact-alarm access or establish Play eligibility for `USE_EXACT_ALARM`; the Android [alarm scheduling guide](https://developer.android.com/develop/background-work/services/alarms) describes the platform APIs and timing behavior, while Play exact-alarm eligibility is covered in the [sensitive permissions topic](../sensitive-permissions/sensitive-permissions.en-US.md).

### Additional Play location review for location FGS

Play has a separate location-permission review for location FGS. The current [background location permissions help article](https://support.google.com/googleplay/android-developer/answer/9799150?hl=en) says some FGS uses may be approved, but the service must continue an in-app, user-initiated action and stop immediately when that action is complete. If FGS-based location is equivalent to `ACCESS_BACKGROUND_LOCATION` or otherwise constitutes background location, the background-location review also applies, including its declaration, video, prominent disclosure, and privacy-policy requirements. An Android `location` type, background-start exemption, or system permission grant is not Play approval.

Play also has a separate minimum-scope policy for foreground precise location: its current [policy article](https://support.google.com/googleplay/android-developer/answer/17033915?hl=en) says that apps targeting Android 17/API 37+ must use the Android Location Button for transactional, one-time precise-location use cases; the Play Console `ACCESS_FINE_LOCATION` declaration is scheduled to open in **November 2026**, with compliance required starting **2027-01-27**. The Location Button is for foreground, transactional access; it does not replace background-location review or change the separate geofencing FGS deadline. Android's [Location Button documentation](https://developer.android.com/guide/topics/permissions/private-alternatives/location-button) describes implementation and manifest prerequisites only; Play eligibility and declarations come from Play policy.

### Power management, background starts, and Play allowlisting

Play's [Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en) policy requires compliance with Android system optimization requirements and prohibits apps that are not eligible for allowlisting from bypassing system power management. It directly references Android's [Core App Quality guidelines](https://developer.android.com/docs/quality-guidelines/core-app-quality), which include avoiding unnecessary long-running background services and meeting the default optimization requirements. Android's [Doze and App Standby guide](https://developer.android.com/training/monitoring-device-state/doze-standby.html) describes system deferrals for background work, jobs, and ordinary alarms, and expressly says not to start an FGS just to prevent App Standby from treating the app as idle. Direct requests to ignore battery optimizations are limited to the cases listed in that guide. The Android FGS-start guide separately lists the user turning off battery optimizations as one background-start exemption; that is not the same as Play allowlisting eligibility or a blanket Doze exemption. Evaluate system start conditions and Play eligibility separately.

## Additional Android 15/API 35 runtime restrictions

These system behavior changes apply to apps targeting Android 15 or higher. They add runtime constraints; they do not replace Play's user-benefit, core-function, or Console-declaration review.

- `dataSync` and `mediaProcessing` can each run for up to six hours in a rolling 24-hour period; multiple services of the same type share that type's quota. Bringing the app to the foreground resets the timer. When the limit is reached, Android invokes `Service.onTimeout(int, int)`. The service must call `stopSelf()` within a few seconds or the system raises an exception. Once the quota is exhausted, the app cannot start another service of that type until the user brings it back to the foreground.
- `mediaProcessing` is for long-running media work such as transcoding; it is not a generic label for downloads or background computation. Prefer WorkManager or another suitable API when the task can be deferred.
- Starting with Android 15, a `BOOT_COMPLETED` receiver cannot launch `dataSync`, `camera`, `mediaPlayback`, `phoneCall`, `mediaProjection`, and several other FGS types. The microphone restriction has applied since Android 14.
- For apps targeting Android 15, `SYSTEM_ALERT_WINDOW` alone no longer exempts an app from background FGS-start restrictions. If relying on this exception, a visible overlay window must exist before the service starts; otherwise the app may receive `ForegroundServiceStartNotAllowedException`.

Android recommends implementing the timeout callback, enabling the relevant compatibility changes on test devices, and regression-testing timeouts, boot broadcasts, and overlay visibility. See [Android 15 behavior changes](https://developer.android.com/about/versions/15/behavior-changes-15), [Android 15 foreground-service types](https://developer.android.com/about/versions/15/changes/foreground-service-types), and the [Service API](https://developer.android.com/reference/android/app/Service) for APIs, suitable alternatives, and test commands.

### Android 16/API 36: background jobs started by an FGS still have quotas

Starting with Android 16, background jobs started by an FGS remain subject to the runtime quotas for their job type. Android explicitly includes jobs scheduled directly with `JobScheduler` and jobs created by libraries such as WorkManager and DownloadManager. For data transfers in response to a user action, Android recommends considering UIDT; UIDT jobs are exempt from ordinary job quotas but remain subject to system-health conditions and stop rules. Play's UIDT policy still requires a user-initiated network transfer that runs only as long as necessary. Choosing UIDT does not establish Play FGS approval or expand Play's FGS exceptions. See [Android FGS changes](https://developer.android.com/develop/background-work/services/fgs/changes), the [UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt), and [background data-transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options).

## Geofencing: Play change effective January 27, 2027

In an April 2026 policy preview, Google announced that geofencing will no longer be an approved FGS use case effective **2027-01-27** and recommends the Android Geofence API instead. The Policy Deadlines table lists the same date. Before the deadline, review code, permissions, Console declarations, and disclosures as part of the migration.

The Geofence API monitors enter/exit events through location services and notifies the app through a `PendingIntent`; the receiver can start suitable short background work or show a notification. This avoids the need to keep a location FGS running continuously, but it **does not remove background-location permission or policy obligations**: geofencing handles location while the app is not in use. If the feature needs `ACCESS_BACKGROUND_LOCATION`, the app still needs to justify it under the location policy and disclose it prominently. Also check Android-version behavior, user grants, SDKs, and Play review tracks.

### Android geofencing best practices

- Android's current guide treats geofencing as background location. Use it only when a core feature needs it; prefer foreground or coarse access when sufficient, explain why background access is needed, and degrade gracefully after denial or revocation. Android best practices do not guarantee Play approval.
- The geofencing guide lists `ACCESS_FINE_LOCATION` and says apps targeting Android 10/API 29+ also need `ACCESS_BACKGROUND_LOCATION`. Check the current Android version, actual accuracy requirement, and Play's background-location rules; system permission is not Play authorization.
- The guide recommends a radius of at least about **100–150 meters**. Wi-Fi, indoor conditions, network-location availability, and device state all affect accuracy and delivery. Background events are measured in minutes; do not promise second-level delivery. The API is not recommended on Wear OS because of poor power efficiency.
- For features that tolerate delay, increase notification responsiveness and consider a larger radius for places where users spend time. Use `DWELL` and a loitering delay to reduce alerts from brief boundary crossings. Responsiveness is best-effort, not an on-time SLA.
- Remove geofences when the feature no longer needs them; an expiration duration can also let the system remove them automatically. The system restores registrations after Google Play services upgrades, resource-driven restarts, and location-process crashes; the app generally **does not need to re-register** for those events. Re-register only if the feature still needs the fences after device reboot, reinstall, app/Play services data clearing, or a `GEOFENCE_NOT_AVAILABLE` event.
- Troubleshoot by checking permissions, Location Services/Location Accuracy, radius, Wi-Fi/network location, and data connectivity. `GEOFENCE_NOT_AVAILABLE` means the service is currently unavailable. Explain system-setting needs and let users choose whether to enable them; do not silently change system settings. Ordinary apps targeting Android 10+ cannot turn Wi-Fi on directly and should use the system Settings Panel.
- If a user-initiated location task needs access to continue after the UI closes, Android's privacy guide recommends starting an eligible location FGS while the Activity is visible. That implementation must still satisfy Play's FGS rules, and the geofencing FGS use case remains subject to the January 27, 2027 change.

These are Android implementation and UX recommendations. Play's core-function, necessity, user-expectation, permission-declaration, and location-disclosure rules still apply separately.

## Release checklist

1. Inventory every service, SDK, and merged manifest: type, trigger, duration, notification, and permissions.
2. For each service, explain why work must start immediately or remain perceptible; move deferrable or batchable work to WorkManager or another suitable background API.
3. For Android 14+ targets, verify each manifest permission and Console declaration; make the description, user impact, use case, and video show the same real workflow.
4. For location FGS, geofencing, and other background location behavior, review `ACCESS_BACKGROUND_LOCATION`, Play's location declaration, prominent disclosure, privacy policy, and SDK behavior.
5. Before **2027-01-27**, remove geofencing as an FGS use case from implementation and form materials, migrate to the Geofence API, and reassess location permissions.
6. Handle `USE_FULL_SCREEN_INTENT` as a separate policy topic; it is not an FGS type declaration or the same permission.

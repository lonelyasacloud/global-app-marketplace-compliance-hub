## Current requirements

### Submission requirements for new apps and updates

Starting **August 31, 2026**, new apps and updates must meet the following target API levels to be submitted. Use Google's current date table for the latest requirements.

| App type | Required target API | Effective date |
| --- | ---: | --- |
| Phones, tablets, and Android Auto | Android 16 / API 36 or higher | August 31, 2026 |
| Wear OS | Android 15 / API 35 or higher | August 31, 2026 |
| Android Automotive OS | Android 15 / API 35 or higher | August 31, 2026 |
| Android TV | Android 14 / API 34 or higher | August 31, 2025 |
| Android XR | Android 14 / API 34 or higher | August 31, 2026 |

### Discoverability requirements for existing apps

This is a separate rule. An existing app below its target threshold is not available to new users on Android versions higher than the app's target API. Existing users are not thereby prevented from using, rediscovering, or reinstalling the app, subject to the Android versions the app supports.

| App type | Minimum target API for existing apps | Effect below the threshold |
| --- | ---: | --- |
| Phones, tablets, and Android Auto | Android 15 / API 35 | Not discoverable to new users on devices running a newer Android version than the app target |
| Wear OS | Android 14 / API 34 | Same |
| Android TV | Android 13 / API 33 | Same |
| Android XR | Android 14 / API 34 | Same |
| Android Automotive OS | Android 12L / API 32 | Same |

New users whose device OS is at or below the app's target API may still see an outdated app. When a user follows a Play Store deep link from a newer device, Google Play may say the app was built for an older Android version and cannot be installed on that device.

## Extensions, eligibility, and leaving distribution

- An impacted, noncompliant app can request continued broad distribution through **November 1, 2026**. Google says only apps that are not compliant receive a Play Console warning/notification; the form is linked from the relevant warning or issue details on the Policy status page. It is not a public form available to every developer.
- Public Help pages cannot confirm whether a particular account or package received the form, qualifies, or was approved. Check the app's Play Console notification and Policy status page.
- Existing users are not affected by the restriction: Google says they can still discover, reinstall, and use the app on Android versions it supports.
- If the app should no longer be offered to new users, it can be unpublished in Console. Existing users can continue to use it and receive updates; new users will not find or download it on Google Play. The Console workflow and account status require sign-in.
- The stated exception is for **permanently private apps restricted to users in a specific organization and intended only for internal distribution**. Calling an app an “enterprise app” or requiring sign-in does not by itself establish eligibility.

## Target API versus minimum OS version

`targetSdkVersion` (configured in Gradle or the manifest) declares which Android behavior rules the app is prepared to follow. It differs from `minSdkVersion`: raising the target does not by itself prevent the app from running on older Android releases; actual minimum compatibility is determined by `minSdkVersion` and related configuration. Check the final build artifact and merged manifest, not only the source tree, to verify what is submitted to Play.

### Separate Google Play compatibility release gate: 16 KB memory pages

This is a release requirement separate from the API 36 date matrix: apps distributed on Google Play and targeting Android 15 / API 35 or higher must support 16 KB memory pages on 64-bit devices. Starting **February 1, 2027**, updates that do not support 16 KB pages cannot be released. Android 16's 4 KB compatibility mode is a device-side compatibility/testing aid, not a long-term substitute for this Play release requirement.

Google says apps using only Java/Kotlin (including all libraries and SDKs) already support 16 KB. If the app, a third-party SDK, or an app builder includes native `.so` libraries, check and update each one. Verify ZIP/ELF alignment in the AAB and Play-generated package, then test in a 16 KB environment. Google recommends AGP 8.5.1+, NDK r28+, and compatible prebuilt dependencies. See [Support 16 KB page sizes](https://developer.android.com/guide/practices/page-sizes). This is an independent Play compatibility gate with its own deadline; it is not the same as meeting the API 36 target requirement.

### Direct tools and engine guidance for 16 KB migration

These are implementation/testing references; they do not change Play's February 1, 2027 release gate. The Android guidance emphasizes checking **every native library and ABI in the final package**, not only source code or a vendor's general compatibility claim:

- **Packaging and ELF alignment:** For uncompressed `.so` files, Google recommends AGP 8.5.1+. It warns that builds using AGP 8.3–8.5 may appear to work locally while the APK generated by `bundletool` for Play may remain ZIP-unaligned and fail to install. NDK r28+ uses 16 KB ELF alignment by default; NDK r27 and earlier need linker flags from the guide. Each prebuilt `.so` must also be replaced with a compatible build or rebuilt; check vendor SDKs per ABI. Compressed `.so` files are an older-AGP fallback, but increase installed size and can raise install-failure risk on low-storage devices.
- **Verification:** Test with an Android 15 SDK or newer emulator/device. On the AAB, run `bundletool dump config --bundle=<app.aab> | grep alignment` and confirm `PAGE_ALIGNMENT_16K`; then check the final APK with `zipalign -c -P 16 -v 4 app.apk`. Inspect every 64-bit native library and every ELF `LOAD` segment rather than relying only on the bundle setting or one library. Search code for hard-coded 4096 or fixed page-size assumptions; use `sysconf(_SC_PAGESIZE)` or `getpagesize()` for the runtime size. Play Console's App Bundle Explorer is another compatibility signal, not a replacement for runtime testing in a 16 KB environment.
- **RELRO and runtime crashes:** A `.so` built with NDK r27 or lower can segfault at runtime if its RELRO segment is not compatible with 16 KB pages. Google recommends inspecting `GNU_RELRO` with `llvm-readelf -Wl`. When RELRO shares a `LOAD` segment with subsequent writable data, check `(VirtAddr + MemSz) % 0x4000 == 0`. When RELRO occupies its own `LOAD` segment, also consider the boundary of the next writable segment; do not apply the same modulo result mechanically. ELF inspection supplements runtime testing.
- **Game engines:** The Android Developers [Unity guide](https://developer.android.com/games/engines/unity/unity-on-android), updated February 26, 2026, lists Unity 2021, 2022, and Unity 6 support. The [Unity 6000.0 Android manual](https://docs.unity3d.com/6000.0/Documentation/Manual/android-requirements-and-compatibility.html) recommends 6000.0.38f1 or later, updating native plugins, and checking Unity Editor build warnings for unaligned `.so` files. Unity's official platform post lists older LTS patch versions subject to support-channel/version updates; recheck current Unity release notes before using them. The Android Developers [Unreal on Android](https://developer.android.com/games/engines/unreal/unreal-on-android) page, updated October 7, 2026, says Unreal 5.6+ supports 16 KB. Its linked Epic 5.6 release notes timed out in this fetch, so no further claim is inferred from them.
- **Build upgrades:** The [Android Gradle Plugin Upgrade Assistant](https://developer.android.com/build/agp-upgrade-assistant) can help upgrade AGP and compatible Gradle/third-party plugins. Back up first, review required and recommended steps, then sync, build, and test. It helps with the toolchain upgrade; it does not verify 16 KB compatibility of the AAB/APK.
- **Related references and script limits:** The [NDK prebuilt-libraries guide](https://developer.android.com/ndk/guides/prebuilts) explains selecting prebuilt libraries by ABI. The [zipalign documentation](https://developer.android.com/tools/zipalign) explains `-P 16` and APK-signing order. The Android guide's `check_elf_alignment.sh` link was not readable in Code Search, but its source was opened in the [current AOSP Gitiles branch](https://android.googlesource.com/platform/system/extras/+/refs/heads/main/tools/check_elf_alignment.sh). The current implementation uses `head -1` to take only the first `LOAD` alignment value for each ELF, so an `ALIGNED` result alone does not prove that every other `LOAD` segment meets the requirement; inspect each `objdump -p` line as Google's guide directs. The script's Build Tools `35.0.0-rc3` install hint may be stale; the current Android guide requires Build Tools 35.0.0 or higher. The source may change, so follow the current Android guide.

For custom memory allocators (not Android's standard `scudo` allocator), adjust release thresholds to the runtime page size, fill existing pages densely, align pools to page-size multiples, and release large cached pages promptly. See the Android 16 KB guide for details. Ordinary Java/Kotlin apps do not need to copy these native allocator optimizations, though regression testing in a 16 KB environment is still useful.

## Android 16 behavior-change register (official pages updated October 16, 2026)

Raising the target API enables some platform behavior changes tied to `targetSdkVersion`; other changes affect every app running on Android 16. The sections below keep those groups separate. Most entries are platform compatibility and implementation matters; the Android 16 behavior lists do not themselves add Play obligations, but 16 KB page support has a separate Play release gate (see above). For health, photo, or network permissions, also check Play permission, privacy, and Data safety requirements. The migration guide recommends starting at least three months early and reviewing each major-version change.

### Changes for apps targeting API 36 or higher

| Area | Change and migration check |
| --- | --- |
| System UI and edge-to-edge | On Android 16, API 36 apps can no longer opt out of edge-to-edge; the opt-out still works on Android 15. Check status/navigation bars, cutouts, keyboard insets, and tappable areas. See [Compose window insets](https://developer.android.com/develop/ui/compose/system/insets) and [Views edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge). |
| Back navigation and fonts | Predictive Back animations are enabled by default; `onBackPressed` is no longer called and `KEYCODE_BACK` is no longer dispatched. Migrate to supported APIs and treat opt-out as temporary. `elegantTextHeight` is ignored at target API 36; check text layouts for Arabic, Lao, Myanmar, Tamil, and other listed scripts. See the [Predictive Back migration guide](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture). |
| Large-screen adaptation | On large displays with smallest width of at least 600dp, orientation, resizability, and aspect-ratio restrictions are ignored in full-screen and multi-window modes. Exceptions include games, users explicitly selecting the old behavior in system settings, and screens below `sw600dp`. Test folding, rotation, multi-window, and state preservation. The compatibility opt-out is temporary and does not continue at API 37. See [Adaptive Apps](https://developer.android.com/adaptive-apps). |
| Fixed-rate work | If `scheduleAtFixedRate` misses multiple executions due to process lifecycle limits, at most one missed execution runs immediately when the app returns. Check timer/synchronization logic that assumes all missed executions are replayed. |
| Health permissions | For relevant APIs in API 36-targeting apps, `BODY_SENSORS` / `BODY_SENSORS_BACKGROUND` are replaced by granular `android.permission.health` permissions such as `READ_HEART_RATE` and `READ_HEALTH_DATA_IN_BACKGROUND`. Mobile apps also need an Activity to display the privacy policy and an adequate permission rationale. Reconcile this with the [Health Connect guide](https://developer.android.com/health-and-fitness/health-connect) and Play health-data declarations. |
| Local network privacy | Android 16 describes a staged, developer opt-in protection test; this is not an API 36 Play declaration deadline. Protected local TCP/UDP, multicast/broadcast, and `.local` discovery traffic may require Nearby devices permission. Test casting/device discovery under denial and revocation, and follow the platform's later permission design. |
| Photo and video selection | On Android 16, the system photo picker preselects app-owned media when an app targeting SDK 36+ requests photo/video access. Users can deselect those items, which revokes access. Do not treat preselection as permanent authorization; handle the actual URI grant. |
| Bluetooth and security | The page adds bond-loss/encryption-change broadcasts and a public API to remove a bond for an associated device; OEM broadcast behavior may vary, so retain fallback handling. `MediaStore#getVersion()` becomes unique per app and must not be used to infer device data. Safer Intents strict matching is an explicit opt-in in API 36. Mali GPU IOCTL filtering is specific to certain Pixel/Mali devices and is not a general Play review rule. |

### Changes affecting all apps running on Android 16

| Area | Change and migration check |
| --- | --- |
| Background job quotas | JobScheduler quotas depend on standby bucket, whether a job started while the app was foregrounded, and concurrent foreground services. WorkManager, JobScheduler, and DownloadManager can be affected. Inspect stop reasons; assess [User-Initiated Data Transfer jobs](https://developer.android.com/develop/background-work/background-tasks/uidt) for user-initiated transfers instead of using a generic foreground service to bypass quotas. Google also recommends `getPendingJobReasonsHistory` for diagnosis. |
| Job lifecycle | Abandoned jobs that lose a strong `JobParameters` reference can receive `STOP_REASON_TIMEOUT_ABANDONED`; frequent occurrences may reduce scheduling frequency. WorkManager, AsyncTask, and DownloadManager manage their job lifecycle and are not affected by this specific issue. `setImportantWhileForeground()` is ineffective and `isImportantWhileForeground()` returns `false`. |
| Broadcast order and ART | Broadcast priority is no longer globally ordered across processes and is constrained within system-defined bounds; use explicit coordination for cross-process work. Avoid non-SDK/ART internals because ART modules can also update through Google Play system updates on older Android versions. See [non-SDK interface restrictions](https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces). |
| 16 KB memory pages (platform behavior) | Android 16 offers compatibility mode and a prompt for some 4 KB-aligned apps; this only describes device-side compatibility. A separate Google Play release gate blocks updates from February 1, 2027 for apps targeting API 35+ that do not support 16 KB pages. See the section above and the [official guide](https://developer.android.com/guide/practices/page-sizes). |
| Accessibility and navigation | `announceForAccessibility` / `TYPE_ANNOUNCEMENT` are deprecated. Choose pane titles, Live Regions, or error semantics according to the UI change. For apps already migrated to Predictive Back, long-pressing Back in three-button navigation can preview the transition. |
| Icons and projected displays | Beginning with Android 16 QPR 2, the system can theme app icons that lack a monochrome layer. Virtual device owners can override orientation/aspect-ratio/resizability on managed virtual devices; test projected use on car displays and Chromebooks. |
| Intent and pairing privacy | Intent redirection protections are hardened by default; disable them only for a confirmed legitimate compatibility need. Companion-device pairing no longer directly notifies an app of discovery timeout: the system first shows a user dialog, then sends `RESULT_USER_REJECTED` after dismissal. |
| Bluetooth bond loss | If reconnection authentication fails, the system disconnects the link, retains local bond information, and prompts the user to pair again. Use this alongside the target-specific broadcast changes, accounting for OEM variation. |

These two checklists do not replace the migration chain. Review every Android major version between the app's current target and API 36, plus the SDKs/APIs the app actually uses. Cross-check permission changes against [Sensitive permissions](../sensitive-permissions/sensitive-permissions.en-US.md), Health apps and Health Connect (snapshot: `health-apps-and-health-connect-en.md`, not imported in this repository), [Photo/Video permissions](../photo-video-permissions/photo-video-permissions.en-US.md), [Background location](../background-location/background-location.en-US.md), and [Permissions declaration review](../permissions-declaration/permissions-declaration.en-US.md).

An API migration can also touch separate Play requirements or declarations for permissions, health data, location, photos/videos, and foreground services. Passing the target API submission check does not automatically pass sensitive-permission review, Data safety, or Console declarations. See [Sensitive permissions and APIs](../sensitive-permissions/sensitive-permissions.en-US.md), [Photo/Video permissions](../photo-video-permissions/photo-video-permissions.en-US.md), [Background location](../background-location/background-location.en-US.md), and [Permissions declaration review](../permissions-declaration/permissions-declaration.en-US.md).

## Suggested migration sequence

1. Confirm the app category, form factors, active packages and tracks in Play Console/artifacts; record current `targetSdkVersion`, `minSdkVersion`, and each applicable threshold.
2. Follow the Android migration guide through each major version between the current and target API. Do not skip directly to the API 36 page.
3. Update Android Gradle Plugin, build tools, SDKs, and libraries; check third-party SDK compatibility and permissions in the merged manifest.
4. Define test scenarios for edge-to-edge, back navigation, large/foldable screens, background work, Intent security, local network, and health/photo permission denial. Verify on Android 16 devices/emulators and supported earlier versions.
5. Reconcile Play policy forms, sensitive-permission declarations, privacy disclosures, and health/photo/location permissions with the target API changes.
6. Verify the final AAB target API, version, and all form-factor tracks before release; retain test results and Console records.

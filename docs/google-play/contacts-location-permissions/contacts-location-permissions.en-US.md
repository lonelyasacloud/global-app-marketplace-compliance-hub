## Choose the minimum access path

| Use case | Preferred path | When broad access may be considered |
| --- | --- | --- |
| A user selects one or more contacts to share, invite, message, or fill a form | Use Android Contact Picker and request only the fields needed for that flow | Consider `READ_CONTACTS` only when Contact Picker cannot support a core feature promoted in the store listing and the declaration explains why the alternative is insufficient |
| A user briefly searches nearby, shares a current location, tags content, or fills an address | For one-time precise location on Android 17/API 37+ targets, use the system Location Button; use coarse location when city/region accuracy is enough | Consider unrestricted, persistent `ACCESS_FINE_LOCATION` only when coarse location and the Location Button cannot support a core feature. A button-only Manifest may still declare `ACCESS_FINE_LOCATION` with `onlyForLocationButton`; current Play Help still requires a Console declaration for every app requesting that permission |

Contacts and location are personal and sensitive data. ## Contacts Permissions

- **Scope:** Apps targeting Android 17 / API 37 or higher may request `READ_CONTACTS` only when Android Contact Picker is insufficient for their core functionality.
- **Play Console:** Apps that continue to request `READ_CONTACTS` must submit a declaration describing the contact fields needed, the core feature they support, and why Contact Picker is technically insufficient. The Help article says developers with `READ_CONTACTS` began receiving Console declaration prompts in September 2026.
- **Disclosure boundary:** Do not disclose or publish non-public contact data unless authorized by the data subjects themselves. A permission grant is not blanket consent to upload, publish, or repurpose an address book.
- **Date:** This new policy is scheduled to take effect January 27, 2027.

### Contact declaration use cases and boundaries

The Play declaration options include contact management; dialing or SMS; call history; CRM; call screening; accessibility; personal assistants; friend matching/search; backup/restore/device migration; autocorrect/autocomplete; user-initiated contact selection; and “Other.” These are declaration categories and examples, not automatic approval. The declaration must also explain why the Contact Picker is insufficient for the core feature.

The Help article says apps that only need contacts to share files, collaborate, invite/refer people to a service, or select one contact for a transaction typically should not request broad `READ_CONTACTS`. A custom contact picker is not a reason to retain the permission. Private apps and enterprise device-management apps are exempt from this Contacts-policy requirement; confirm that the app meets the official category definition.

### Contact Picker implementation notes

The Android 17/API 37 system picker lets an app request specific data fields and lets the user choose contacts or individual data items. The preferred API action is `ContactsPickerSessionContract.ACTION_PICK_CONTACTS`; the contract and its `Session` class were added in API 37. The result is a session URI granting one-time read access to the selected fields, without `READ_CONTACTS`. The picker is not backported to earlier Android versions.

- Set the required `EXTRA_PICK_CONTACTS_REQUESTED_DATA_FIELDS` list to only the MIME types the feature uses. Android's current API reference allows structured name, email, phone, postal address, organization, relation, event, photo, group membership, website, and nickname data. Unsupported MIME types cause `IllegalArgumentException`. An SMS invite flow should request phone data only.
- By default, a contact appears when it has at least one requested data field. Set `EXTRA_PICK_CONTACTS_MATCH_ALL_DATA_FIELDS` to `true` only when every requested field is required for a valid selection; otherwise the default `false` is more inclusive.
- The picker defaults to single selection. Add `Intent.EXTRA_ALLOW_MULTIPLE` to permit multiple contacts. `EXTRA_PICK_CONTACTS_SELECTION_LIMIT` defaults to 50 and accepts at most 100; set a smaller limit when the feature needs fewer recipients.
- Query only the session URI returned for the completed selection. Do not query the provider's base `Session.CONTENT_URI`, and do not pass custom `selection` or `selectionArgs`; the API reference says those arguments are unsupported. Handle the cursor off the main thread as shown in the guide's sample.
- When a contact has several email addresses or phone numbers, group rows with `ContactsContract.Contacts.LOOKUP_KEY` and expose entry labels such as work or personal when the UI needs to distinguish them. Account-specific metadata is stripped from results.
- Session access is temporary. If a user-facing feature needs selected values after process death, persist only the necessary data and retain it only for the disclosed purpose; the selection itself does not justify general address-book retention.
- For apps targeting Android 17/API 37, `ACTION_PICK` is automatically upgraded to the system picker, but use `ContactsPickerSessionContract.ACTION_PICK_CONTACTS` and its extras for multiple fields and session-based results. The Play Help preview uses the label `Intent.ACTION_PICK_CONTACTS`; check the current Android API symbol rather than copying the preview's name blindly. On Android 17 devices with a lower target SDK, the guide describes an extra that enables testing the system picker.

The official Contact Picker guide's three sample links currently point to one [pinned GitHub commit](https://github.com/android/snippets/blob/e72c9d1fdc9658b16537b8b137ba517e229b02ab/contacts/src/main/java/com/example/contacts/ContactPickerActivity.kt). That exact commit and its raw mirror returned cache misses on October 22 and 23, 2026; the guide itself contains current inline examples. An older linked commit was opened earlier and remains historical evidence, not proof of the newer file's contents. As separate supplemental evidence, the same-path file on the official repository's [`main` branch](https://github.com/android/snippets/blob/main/contacts/src/main/java/com/example/contacts/ContactPickerActivity.kt) was readable on October 23: it requests email/phone fields through `ACTION_PICK_CONTACTS`, demonstrates single selection, multiple selection (sample limit 5), and phone-only selection, then queries only the returned Session URI on `Dispatchers.IO`, projects lookup key/display name/MIME/data, and groups rows by `LOOKUP_KEY`. It avoids custom `selection`/`selectionArgs`, handles an unavailable picker, and its file header declares Apache 2.0. Because `main` is mutable, this comparison does not establish that the pinned e72 commit has identical content. The code sample is Android implementation guidance and does not expand Play permission eligibility. On October 22, the relevant body sections of the official [ContactsPickerSessionContract API reference](https://developer.android.com/reference/android/provider/ContactsPickerSessionContract) and its nested [Session API reference](https://developer.android.com/reference/android/provider/ContactsPickerSessionContract.Session) were reopened directly. The large API pages were reviewed only for members relevant to this topic, not exhaustively.

### New: writing contacts and `MANAGE_CONTACTS` (October 21, 2026)

On October 21, Android announced a change to contact writes in the upcoming Android release. This is a **separate permission branch** from the `READ_CONTACTS` minimum-scope policy above: the existing policy governs broad address-book reads, while this change covers direct creation/modification and communication-directory integrations.

- **User-driven, single-contact add or edit:** Use `ACTION_INSERT`, `ACTION_EDIT`, or `ACTION_INSERT_OR_EDIT` to open the system contacts editor and prefill data with standard extras. Android's guide recommends intents for modifying a single contact. The user can review and save; the app does not need direct write access.
- **OS release and target SDK:** The standardized contact editor is planned for the 2027 Android release. Apps targeting that release or later that still write directly through `WRITE_CONTACTS`/`ContactsContract` will have writes rejected, with a `SecurityException` or permission denial. The blog says apps targeting older releases keep current behavior, while the standardized intent editor will be available to apps on the new OS.
- **`MANAGE_CONTACTS`:** A special app access permission planned for Android 17 QPR2 (Q4 2026), for the small set of apps whose core use requires broad or background contact management and cannot be supported by contact intents. Google's examples of potentially qualifying cases include dedicated contact-manager/dialer replacement apps, bulk caller-ID/spam updates, two-way enterprise/cloud sync, bulk backup/restore/device transfer, and per-contact ringtones. Keeping a branded custom editor alone is not enough. The permission covers reading, adding, editing, and deleting contacts, accounts, and People Directory data, so a separate `READ_CONTACTS` request is unnecessary; users enable it in Special app access settings, not through a runtime dialog. The API 37.2 [Settings.ACTION_MANAGE_CONTACTS](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_CONTACTS) intent opens the user-managed special-access settings screen; a matching activity may not exist on every device. This settings entry does not establish Play approval or replace the Play Console declaration.
- **Play declaration:** The blog says publishing an app on Google Play with `MANAGE_CONTACTS` will require a Play Console declaration explaining why contact intents cannot support the app's core functionality. It dates the declaration and policy compliance to “2027, not earlier than the upcoming Android release,” with no exact calendar day. Do not conflate this with the existing `READ_CONTACTS` policy's **January 27, 2027** date.
- **People Directory:** VoIP/messaging apps that currently insert “Call with this app”/“Message with this app” rows into users' address books should migrate to the system People Directory. The blog says it is planned for Android 17 QPR2 (Q4 2026). The current `PeopleContract` API reference describes a registered provider, system aggregation/queries, and a system-protected `PendingIntent` to initiate interactions; that reference also says reading the People Provider requires `MANAGE_CONTACTS`. This is Android platform API documentation, not a separate Play-policy exemption.
- **Migration checks:** Search the manifest/code for `WRITE_CONTACTS`, `RawContacts.CONTENT_URI`, `Data.CONTENT_URI`, and `applyBatch(ContactsContract.AUTHORITY, …)`. Replace user-driven writes with intents, publish People Directory data using its standard contract, and remove `WRITE_CONTACTS` after the last direct-write path is gone. The system editor ignores custom MIME types; `SHOW_OR_CREATE_CONTACT` is inconsistent across devices, so prefer `ACTION_INSERT_OR_EDIT`. Test real devices and target-SDK combinations on Android 17 QPR2 and the upcoming release. The blog also introduces the upcoming `EXTRA_PHOTO_URI` photo-prefill capability. The successful October 23, 2026 read of the `ContactsContract.Intents.Insert` reference did not list that symbol; a retry on October 24 timed out, and a targeted lookup returned Internal Error, so this pass could not confirm whether the reference changed. Do not treat the unreleased preview as a current API guarantee; recheck the SDK/reference when it is accessible after the new release.

## Location Permissions: foreground precise location

### One-time or session-based location

For apps targeting Android 17 / API 37 or higher, the Android Location Button is required when a feature needs precise location only for a brief, user-triggered transaction. Examples include searching nearby, sharing a current location once, tagging a photo/post at the user's request, and filling a delivery address.

The Location Button limits precise access to the current session and only triggers it after a user action. Its access expires when the session ends. The system button can be styled within the allowed colors, outline, size/shape, and predefined text options, but its location icon cannot be customized and its font size is system-managed for accessibility. Android's implementation guide currently describes the Jetpack library as experimental, so check its latest compatibility status before shipping.

Implementation also requires `android.permission.USE_LOCATION_BUTTON` for the system's remote-rendering service. If the app obtains precise location only through the button, set the `onlyForLocationButton` flag on `ACCESS_FINE_LOCATION` to prevent the app from switching to the broader precise-permission path. On Android 16 and lower, the Jetpack library falls back to a locally rendered button that triggers the standard location permission prompt; those OS versions do not get Android 17's system session-scoped authorization experience.

The Android guide shows this Manifest shape. If the app has another approved persistent-location use case, adjust the flag and permissions to match actual use; do not copy the button-only configuration blindly:

```xml
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
    android:usesPermissionFlags="onlyForLocationButton" />
<uses-permission android:name="android.permission.USE_LOCATION_BUTTON" />
```

### When coarse location is enough

Google Play's minimum-scope Help article gives design examples that do not need street-level precision: showing city-level news, events, or weather; showing that a community member is in the same city or filtering by an approximate distance instead of exposing a live coordinate; finding nearby stores; and choosing language, currency, or local promotions by broad region. These examples are reasons to test whether coarse location can meet the user need, not automatic exemptions or approval categories. The source also asks whether users would reasonably expect a feature to need the requested precision.

### `ACCESS_FINE_LOCATION` declaration and persistent precise access

The current [minimum-scope foreground-location Help article](https://support.google.com/googleplay/android-developer/answer/17033915?hl=en) explicitly requires every app requesting `ACCESS_FINE_LOCATION` to complete a Play Console declaration. The declaration is expected to open in November 2026; the Policy Deadlines table currently gives January 27, 2027 as the exact mandatory date. The Help article says a 30-day self-extension will be available in Play Console; actual eligibility must be checked in the account. Its FAQ separately anticipates enforcement in late January 2027 and says the timeline may be finalized based on developer feedback. Keep that forecast distinct from the exact date in the table.

**The Location Button is not a declaration exemption for `ACCESS_FINE_LOCATION`.** Android's [Location Button implementation guide](https://developer.android.com/guide/topics/permissions/private-alternatives/location-button) still declares `ACCESS_FINE_LOCATION` in its button-only Manifest example, restricted with `onlyForLocationButton`, and also declares `USE_LOCATION_BUTTON`. That flag narrows the Android access path; current Play Help does not say that it waives the Play Console declaration. Check the actual Manifest and Console form before release; do not treat session-scoped access as a no-permission or no-declaration path.

The declaration must map to user-facing features. For unrestricted or persistent precise access, explain why coarse location and the Location Button are both insufficient and why access is essential to a core feature promoted in the store listing. Examples include nearby search, one-time sharing, live tracking, user/automatic tagging, personalization, navigation, area-triggered actions, nearby devices, browser location, and network diagnostics. These categories are not an approval list.

Persistent precise access may be justified only when essential to the core functionality promoted in the store listing. Do not request location solely for advertising or analytics, and never sell device location data. Access while the app is not visible is a background-location use case and must be assessed separately under the [background location policy](https://support.google.com/googleplay/android-developer/answer/9799150?hl=en); the Location Button does not replace that review.

## Release checklist

1. Inventory `READ_CONTACTS`, `ACCESS_FINE_LOCATION`, and their access points across the manifest, SDKs, code, and runtime flows.
2. For each access point, document the corresponding store-listed core feature, trigger, data fields, retention, and recipients.
3. Contacts: establish why Picker is insufficient before deciding on broad access; prepare the Play Console declaration and a process for authorization from data subjects.
4. Location: distinguish coarse/precise, one-time/persistent, and foreground/background access. Move one-time session-based precise access to the Location Button; prepare a technical justification and declaration for persistent precise access.
5. Keep reasonable functionality when a permission is denied or revoked; do not pressure users to grant access.
6. Align the privacy policy, Data safety answers, in-app disclosures, and SDK review with actual data flows.
7. Recheck the Policy Deadlines page and Console forms in November 2026 and before January 27, 2027. Preview text, declaration fields, and enforcement state can change.

This strengthens the least-privilege conclusion: the picker gives the user control over both the contact selection and requested fields. If the feature only needs a recipient for an SMS, requesting `READ_CONTACTS` grants broader access than that interaction requires. The technical API does not change Play's assessment of core-function necessity, exemption categories, or Console declarations.

Implementation notes: request only the data fields the feature needs; for an SMS recipient, request only phone numbers. Group multiple numbers or email addresses using `LOOKUP_KEY` and let the user choose the intended entry. Session URI access is temporary, so persist data that the app needs after its process ends while access is available. Do not rely on account metadata that the picker strips. For target API 37+, the system upgrades legacy `ACTION_PICK` to the new picker UI; migrate to the new session contract/intent extras to use multi-field requests, the single-URI result, or personal/work profile switching. Session URIs do not support custom `selection` or `selectionArgs`.

### Current Android guide recheck: Location Button use and design constraints

The Android Developers guide [Request session-based location access with the location button](https://developer.android.com/guide/topics/permissions/private-alternatives/location-button) was reopened on October 22, 2026; it says it was updated September 8, 2026. It recommends the button for user-initiated, session-scoped precise-location tasks such as nearby search, one-time location sharing, check-ins/location tags, and address autofill. For apps targeting Android 17/API 37+ whose location features all need only session access, the separate Play policy makes the button mandatory.

The guide permits limited styling (background/icon colors, outline, size, shape, and predefined text). The location icon remains mandatory and non-customizable, and the font size is system-managed for accessibility. The Manifest needs the relevant coarse/fine permissions plus `USE_LOCATION_BUTTON`; `onlyForLocationButton` can restrict precise access to the button when that is the app's only precise-location path. The Jetpack library is experimental; its current release page lists only `1.0.0-alpha01`, and Android 16/API 36 and lower fall back to a standard location permission prompt. Recheck library status before shipping.

## Core checklist principles

- Request only the permissions required by a user-facing feature. Explain and request access when the feature is triggered; do not request a batch of permissions at app startup.
- Let users continue using the app when a permission is denied or revoked, degrading the dependent feature gracefully. Do not repeatedly pressure users.
- Periodically audit the manifest, runtime calls, and SDK/library permissions. Users generally attribute an SDK's data access to the app. Remove permissions no longer needed.
- Prefer system pickers, temporary URI grants, intents, and purpose-built APIs over broad access to contacts, photos/media, location, and telephony.
- For background location, first determine whether access is critical to core functionality, gives users a clear benefit, and is understandable to them. Android explicitly says these best practices do **not** guarantee Google Play approval for background location.
- Keep actual app/SDK data flows consistent with disclosures, privacy policy, Data safety, and permission declarations. Android runtime permission is not a substitute for a Play Console sensitive-permission declaration.

## Android permission workflow and high-impact descendants

The official [Android permissions overview](https://developer.android.com/guide/topics/permissions/overview) divides the workflow into finding a permission-free alternative, declaring the needed permission, then requesting and checking access according to its type. Check runtime permissions before every use; a previous grant is not permanent. Permission groups are a system-UI organization mechanism. Group membership can change across Android versions, so do not use a group name or its membership as a substitute for checking each permission.

| Workflow/direct child | Checks to implement | Boundary with Play review |
| --- | --- | --- |
| [Minimize requests](https://developer.android.com/privacy-and-security/minimize-permission-requests) | Prefer pickers, intents, approximate/foreground access, and purpose-built APIs; access only the data needed for the current feature | An API alternative can reduce scope but does not waive Data safety, disclosure, or sensitive-permission declarations |
| [Declare permissions](https://developer.android.com/training/permissions/declaring) and [`<uses-permission>`](https://developer.android.com/guide/topics/manifest/uses-permission-element.html) | Review the merged manifest; remove unused permissions; declare hardware features only when needed and mark optional features correctly | A manifest declaration is not Play approval for a use case |
| [Request runtime permissions](https://developer.android.com/training/permissions/requesting) | Request at a user-triggered feature; explain first; check before each access; degrade gracefully after denial, repeated denial, or revocation in Settings | Runtime consent does not replace Play prominent disclosure, consent, data-safety, or restricted-permission requirements |
| [Explain sensitive access](https://developer.android.com/training/permissions/explaining-access) and [special permissions](https://developer.android.com/training/permissions/requesting-special) | Explain the purpose; check the system Settings grant for each special permission; account for Privacy Dashboard, sensor indicators, and system toggles | Android system authorization and Play Console review/declaration are separate checks |
| [Restrict cross-app interactions](https://developer.android.com/training/permissions/restrict-interactions) | Apply least-privilege component permissions and secure configuration to exported Activities, Services, Providers, and Receivers | Component access control complements data protection; it does not make a sensitive-data use automatically compliant |
| [App permissions best practices](https://developer.android.com/training/permissions/usage-notes) | Do not request a batch at startup; explain denial impact; audit SDKs; test grant/denial/revocation combinations; background location must be core; SMS/call access follows default-handler flows | This is Android implementation guidance; SMS/Call Log, background location, and foreground services remain subject to their respective Play policies |

## Narrower implementation choices

| User task | Android-first option | Relationship to Play policy |
| --- | --- | --- |
| Occasional photo/video selection | Photo Picker; grant temporary read access only to media the user selected | Reduces the need to read the entire media library; photo/video access and User Data requirements still apply |
| Select contacts or an address | Contact Picker; request the fields needed and read only the selected data | Especially relevant to the API 37 contacts changes effective January 27, 2027; see [Contacts and foreground location](../contacts-location-permissions/contacts-location-permissions.en-US.md) |
| One-time precise location | Android Location Button; user click grants access for one session | Suited to a one-time nearby search or address fill; does not replace approval for continuous or background location |
| Open a user-selected file | Storage Access Framework, system document picker, or the app's own file | Do not request broad library access to select one file |
| Take a photo/video | Use the preinstalled camera app through an Intent when that fulfills the task | A feature that controls the camera itself must be assessed separately |
| Pair a nearby Bluetooth device | Companion Device Manager | Can avoid requesting location solely for pairing; check API/version requirements for scanning and connection |
| Read an OTP or a single SMS | SMS Retriever; use SMS User Consent if the message format is not controlled | See [SMS and Call Log permissions](../sms-call-log/sms-call-log.en-US.md); do not request `READ_SMS` by default |
| Enter a phone number, screen calls, or dial | Purpose-built options such as Phone Number Hint, Digital Credentials, `CallScreeningService`, or `ACTION_DIAL` | Avoid expanding phone/call permissions beyond core functionality; restricted SMS/call permissions remain subject to Play rules |
| Scan a barcode | Google Code Scanner; evaluate ML Kit for a custom interface | Can avoid giving the app a camera image stream; data collection and third-party SDK disclosures still apply |

An alternative API can reduce permission scope, but does not waive Data safety, store-disclosure, or SDK responsibilities. Choose based on minimum fields, shortest access duration, and the user action; test denied/revoked access and approximate-only location.

## User data, prominent disclosure, and consent

The Android checklist points developers to the Play Data safety form for collection and sharing. It also calls out data flows that may not be obvious from a permission list, including password fields, authentication, WebView, autofill, data-access auditing, and third-party libraries. Android's Data safety implementation guide states that its category/permission/API examples are **non-exhaustive**; developers must include data collected or shared by their SDKs/libraries and are responsible for accurate declarations. Google may take enforcement action when declarations do not match actual behavior. See the [Data safety topic](../data-safety/data-safety.en-US.md).

### Declare your app's data use: map implementation clues to disclosure categories

Android's official [data-use declaration guide](https://developer.android.com/privacy-and-security/declare-data-use), last updated **March 6, 2026**, supplements the Google Play Data safety form. It organizes common permission, API, SDK, and UI signals across the form's 14 data categories. The guide says its examples are not exhaustive and developers alone remain responsible for accurate declarations. This table is a review map, not an automatic rule that every listed permission means data is collected: verify the actual data read, whether it leaves the device, third-party recipients, and SDK behavior.

| Data safety category | Implementation signals in the guide | Local cross-check |
| --- | --- | --- |
| Location | `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION`, `ACCESS_MEDIA_LOCATION`; location may also be inferred from IP or access-point name | [Foreground/background location](../background-location/background-location.en-US.md), [contacts and location permissions](../contacts-location-permissions/contacts-location-permissions.en-US.md) |
| Personal info | `BIND_AUTOFILL_SERVICE`, `GET_ACCOUNTS`, `AccountManager`; phone-number flows may involve phone/SMS permissions, default dialer/SMS roles, or carrier privileges | [User Data](../user-data/user-data.en-US.md), [SMS/Call Log permissions](../sms-call-log/sms-call-log.en-US.md) |
| Financial info | Google Play Billing Library, Google Pay APIs, and autofill | [Payments, billing, and subscriptions](../payments/payments-and-subscriptions.en-US.md); classify payment-provider data from the actual flow |
| Health and fitness | `ACTIVITY_RECOGNITION`, `BODY_SENSORS`, `BODY_SENSORS_BACKGROUND`, Health Connect, Google Fit, and Sleep API | [Health apps and Health Connect](../health-apps-and-health-connect/health-apps-and-health-connect.en-US.md) |
| Messages | `READ_SMS`, `RECEIVE_MMS`, `RECEIVE_SMS`, `RECEIVE_WAP_PUSH`, `SEND_SMS`, and related permissions | [SMS/Call Log permissions](../sms-call-log/sms-call-log.en-US.md); Play eligibility and Data safety classification are separate checks |
| Photos and videos | Android Photo Picker, media/storage permissions, media-file workflows, and HDR video recording | [Photo and video permissions](../photo-video-permissions/photo-video-permissions.en-US.md); check selection scope and temporary access |
| Audio files | `RECORD_AUDIO`, `CAPTURE_AUDIO_OUTPUT`, and audio workflows in shared storage | [Sensitive permissions](../sensitive-permissions/sensitive-permissions.en-US.md); recording audio and reading user audio files are distinct flows |
| Files and docs | Shared-storage read/write permissions, `MANAGE_EXTERNAL_STORAGE`, storage workflows, and backup | [Sensitive permissions](../sensitive-permissions/sensitive-permissions.en-US.md); Play separately restricts all-files access |
| Calendar | `READ_CALENDAR` and `WRITE_CALENDAR` | Determine whether the app or an SDK actually accesses or transmits calendar data |

| App activity | `AccessibilityService`, `QUERY_ALL_PACKAGES`/installed-app queries, search UI, Shortcuts Integration, and `Instrumentation` | [Sensitive permissions](../sensitive-permissions/sensitive-permissions.en-US.md); Accessibility and broad package visibility have separate Play restrictions |
| Web browsing | Default-browser flows, browsing cache or cookies, and search UI | If the app controls the code/behavior delivered through a WebView, review its collection and third-party transfers |
| App info and performance | APIs such as `ActivityManager`, `ApplicationErrorReport`, `ApplicationExitInfo`, `BatteryManager`, `Debug`, `PowerManager`, `StrictMode`, and `AudioManager` for diagnostics/performance | [Data safety](../data-safety/data-safety.en-US.md), [third-party SDK requirements](../sdk-requirements/sdk-requirements.en-US.md); trace SDKs, purpose, retention, and recipients |
| Device or other IDs | IMEI, MAC, Widevine Device ID, Firebase Installation ID, Advertising ID, `AD_ID`, and IP/access-point-derived identifiers | [Advertising ID](../advertising-id/advertising-id.en-US.md), [User Data](../user-data/user-data.en-US.md); resettable IDs and persistent-identifier association have different rules |

Key boundary: a manifest permission, API call, or SDK is a signal to investigate, not by itself a Data safety declaration. Apply Play's collection/sharing definitions to actual runtime behavior. See the [Data safety topic](../data-safety/data-safety.en-US.md) for on-device processing, end-to-end encryption, service-provider, and other declaration boundaries; separately check whether a permission is allowed under the relevant Play policy.

Prominent disclosure and consent are separate requirements; a privacy policy or Data safety page cannot replace them. Google Play's [best-practices article](https://support.google.com/googleplay/android-developer/answer/11150561) says to:

1. Show the disclosure inside the app, near the permission or capability request; it cannot live only in the store listing or website.
2. Explain why the capability is needed, what data is involved, and how it supports a core feature. If an SDK shares data with a third party, identify the data, purpose, and third-party sharing.
3. Offer at least two choices: consent, or decline/defer. Keep features that do not rely on the data usable after refusal or revocation, and respect repeated denials.
4. Use clear language (the guide uses a 13-year-old reading level as a reference), do not imitate Android system permission prompts, and do not imply the platform has already consented on the app's behalf.
5. If the Play Console declaration requires a video, show app launch, the full disclosure, consent and denial flows, how the user can reach the disclosure again, and the actual core feature using the capability.

The privacy policy must still be supplied in Play Console and inside the app as required. The privacy policy, Data safety declaration, runtime permission prompt, prominent disclosure/affirmative consent, and developer privacy policy are distinct steps and must align.

For UI details, Why/What/How examples, SDK third-party-sharing language, and declaration-video checkpoints, see [External law and reference materials for User Data](../user-data-policy-references/user-data-policy-references.en-US.md). The guide is best-practices material; binding requirements remain in the User Data policy.

## Location, background work, and foreground services

- Many features need location only while the user is using the app; prefer approximate over precise location when sufficient. Consider Companion Device Manager for nearby-device pairing.
- If background location is essential, it should be necessary for core functionality, have a clear user benefit, and be visible to the user. Code review should include SDKs, WorkManager/JobScheduler, AlarmManager, services, and PendingIntent flows that access location.
- Android 8.0/API 26 and higher limit background updates, usually to only a few location callbacks per hour. Do not promise exact, second-level geofence responses.
- A user-initiated, perceptible location task may use an FGS started while the app is visible, under Android's FGS rules; it remains subject to Play FGS type declarations, background-location policy, and the **January 27, 2027 geofencing FGS change**. See [Background location](../background-location/background-location.en-US.md) and [Foreground services and geofencing](../foreground-services-and-geofencing/foreground-services-and-geofencing.en-US.md).

## Identifiers, storage, and security

- Prefer resettable, app-scoped identifiers. Android generally recommends Firebase Installation ID or a privately stored GUID for non-ad uses; avoid long-lived hardware identifiers such as IMEI, serial number, and MAC address.
- Limit Advertising ID to advertising and user analytics; check opt-out on each access, honor reset/deletion, and apply the PII/persistent-ID association rules by purpose. Families adds separate rules for child and mixed audiences. See the [AAID topic](../advertising-id/advertising-id.en-US.md).
- Share data through a restricted ContentProvider or explicit Intent and use one-time grants for sensitive data where possible. Do not put sensitive data in Logcat or log files.
- Internal app storage is better isolated by default than shared external storage, whose contents may be read or modified by other apps. Keep ContentProviders unexported unless needed; then grant only minimum permissions.
- Use HTTPS for network traffic and validate input from external files and Intents. The section below adds the Android security guide's practices for inter-app communication, networking, WebView, permission delegation, storage, and dependency updates.

## Android app security best practices: protect inter-app data and local storage

Android's official [Improve your app's security guide](https://developer.android.com/privacy-and-security/security-best-practices) was last updated **October 16, 2026**. It provides Android implementation guidance, not a separate Google Play approval standard. These practices can reduce exposure and permission scope, but they do not replace review of the User Data, Data safety, or Sensitive Permissions policies.

| Risk area | Android practice | Relationship to Play data duties |
| --- | --- | --- |
| Inter-app transfers | Show the system chooser when an implicit Intent can be handled by multiple apps; use signature-level permissions between apps you own; keep ContentProviders non-exported unless cross-app access is intended. Consider asking for a PIN, password, or biometric before showing sensitive or premium content. | Map recipients, fields, and user expectations in the data-flow inventory. Component permissions control access but do not approve a Play data use. |
| Network and WebView | Use TLS/HTTPS; configure custom CAs with Network Security Configuration rather than trusting arbitrary certificates. Restrict WebView content to controlled origins; enable a JavaScript bridge only when all loaded content is trusted and controlled, and consider HTML message channels for newer communication flows. | Encryption in transit can support the Data safety security-practice declaration, but does not hide collection or sharing. Declare actual destinations, SDKs, and Web content flows. |
| Permission delegation and file sharing | Prefer an Intent when another app can perform the action; use system URI grants for file selection. For cross-app sharing, use `content://`, `FileProvider`, and narrowly scoped one-time read/write URI grants instead of `file://`. | Pickers and Intents can reduce permissions; they do not waive Data safety, prominent disclosure, or restricted-permission requirements. |
| Storage | Prefer the app's internal sandbox for private data. Use app-specific external directories only for non-sensitive files, MediaStore for shared media, and the Storage Access Framework for other shared documents. Check removable-volume availability and validate external-file contents. Put sensitive cache data in internal cache and use `MODE_PRIVATE` for SharedPreferences. | Storage location and access controls are safeguards; separately classify off-device transmission, retention, sharing, and deletion. |
| Platform security components and dependencies | If using Google Play services, check the device security provider asynchronously as described by the guide. Update Android tooling, third-party SDKs, and dependencies and apply available security patches before release. | Developers remain responsible for third-party SDK behavior; use the [third-party SDK topic](../sdk-requirements/sdk-requirements.en-US.md) to check permissions, transmission, retention, and disclosures. |

The body also links to many Android API references and code samples. We opened and recorded the Intent/Provider, network-security, WebView, permission, and file-storage children most relevant to these practices.

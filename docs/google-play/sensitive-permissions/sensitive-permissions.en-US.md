## General rules

Request a permission or API that accesses sensitive information only when it is necessary for a current core feature promoted on the Play listing. Do not request it for an unimplemented, undisclosed, or disallowed feature. Request access incrementally in context and use data only for purposes the user consented to. If a new purpose is added, disclose it and obtain affirmative consent. Data accessed through these permissions is personal and sensitive user data and must also comply with the [User Data policy](../user-data/user-data.en-US.md).

For restricted permissions, honor a user’s refusal, do not manipulate or force consent for non-critical uses, and make a reasonable effort to offer alternatives. Using permissions to bypass platform security/privacy controls or abuse elevated privileges is prohibited.

## Exact alarms: Android system behavior and Play policy

Android answers whether the system will let an app schedule an alarm. Google Play decides whether the app may distribute a permission and what declaration or review it needs. A grant in one layer does not satisfy the other.

| Android version, device, and target SDK | Platform behavior | Play policy relationship |
| --- | --- | --- |
| Android 11/API 30 and earlier | The system does not have the `SCHEDULE_EXACT_ALARM` special app-access model introduced in Android 12. Repeating alarms have been inexact since Android 4.4/API 19; Doze has deferred ordinary alarms since Android 6/API 23. | Play's `USE_EXACT_ALARM` restricted-permission rule is assessed from the submitted manifest/target SDK; an older device does not change the Play requirements for the release bundle. |
| Android 12/API 31+, app targets API 31+ | Exact alarms require the `SCHEDULE_EXACT_ALARM` special app access. Calling an API that requires it without access throws `SecurityException`. On Android 13+ with target API 33+, apps can also choose `USE_EXACT_ALARM`. | Android special access does not establish Play eligibility for `USE_EXACT_ALARM`; that permission is reviewed separately. |
| Android 13/API 33+, app targets API 33+ | `USE_EXACT_ALARM` is granted on install and cannot be revoked by the user. `SCHEDULE_EXACT_ALARM` is user-granted through the Alarms & reminders special-access settings. Do not assume `SCHEDULE_EXACT_ALARM` is pre-granted on a new install targeting API 33+. Check its actual state. | `USE_EXACT_ALARM` is a restricted Play permission. Current criteria limit it to core, user-facing alarm/timer functionality or calendar event reminders requiring precise timing, and require a Play Console declaration and review. For other cases, current Play policy says to evaluate `SCHEDULE_EXACT_ALARM`. |
| Android 14/API 34+, app targets API 33+ | Most new installs are denied `SCHEDULE_EXACT_ALARM` by default; restoring app data to Android 14 also leaves it denied. An existing grant is pre-granted when the device upgrades to Android 14. Android 13+ calendar/alarm apps should evaluate `USE_EXACT_ALARM`. | Platform defaults do not widen Play eligibility for `USE_EXACT_ALARM`. The consolidated Play page also instructs apps to submit a declaration identifying exact-alarm functionality; generic declaration help says Console forms depend on permissions requested in the app bundle that have not already been declared. Check the actual form for the app; do not treat choosing `SCHEDULE_EXACT_ALARM` as Play approval. |
| Revocation and lifecycle | Users and the system can revoke `SCHEDULE_EXACT_ALARM`. Check `AlarmManager.canScheduleExactAlarms()`; when revoked, the app process stops and all future exact alarms are canceled. After the permission-state broadcast, check again and reschedule only what the app still needs. A specific alarm set with an `OnAlarmListener` does not require `SCHEDULE_EXACT_ALARM`. | Honor denial/revocation and degrade gracefully or use a less precise alternative; do not pressure users into granting access. |

### Inexact alternatives, background work, and battery

- Starting with Android 4.4/API 19, all repeating alarms are inexact; the system can batch them to reduce wakeups. Inexact `set()`-style alarms do not fire before the trigger time but can be delayed. For apps targeting Android 12/API 31+, `setWindow()` has a 10-minute minimum window, typically clipped to that floor. Battery-saving restrictions and Doze can delay alarms further.
- Use inexact alarms for most deferrable work. Use WorkManager/JobScheduler for longer, deferrable, or periodic background work; an alarm receiver can enqueue a job. WorkManager periodic work has a 15-minute minimum repeat interval and a flex window, so it does not promise an exact time. For timing while the app process is alive, consider in-process mechanisms such as `Handler`.
- Exact alarms are difficult to batch and increase battery and system-resource use. Ordinary `setExact()` does not promise on-time delivery under every power-saving state. Consider `setExactAndAllowWhileIdle()` only for a user-requested action that truly must happen at an exact time while idle; `setAlarmClock()` is for a real, user-visible alarm and may cause the system to leave low-power modes to deliver it. Exactness is not a general guarantee of background execution.

### Special-app-access request guide and exact-alarm descendants

On October 24, 2026, I reopened Android's [Request special permissions](https://developer.android.com/training/permissions/requesting-special) guide (marked updated October 16, 2026) and followed its exact-alarm example through `AlarmManager`, `Settings`, `Manifest.permission`, and `PowerManager`. The platform workflow is: declare only the special permissions the app actually needs; tie each permission to a user-invoked feature; wait until the user enters that feature; explain the need with an opt-out and settings instructions; then send the user to Special app access in Settings. Unlike a runtime permission, special access is granted in system settings rather than a standard permission dialog. This Android workflow does not establish that Play permits the use case.

### AccessibilityService policy page → Android implementation and accessibility descendants

Reopened [Use of the AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) on October 24, 2026. All 10 body-link occurrences (Help body IDs 3–12) were retried: seven target bodies are readable or opened; `isAccessibilityTool`, `AccessibilityService_description`, and `AccessibilityService_htmlDescription` point to the same `R.styleable` API page, which exceeds 4 MiB and was rejected by the fetch limit. The direct [permission declaration Help article](https://support.google.com/googleplay/android-developer/answer/9214102?hl=en) is readable: it asks for core-functionality details, review instructions and a demo video, plus test-only credentials for restricted content. An active App Bundle on an Open, Closed, or Internal testing track that needs a declaration can block all app changes—including Store Presence, pricing, and distribution—until the developer submits the declaration or removes the permission; unused noncompliant tracks can be deactivated. The narrow multi-APK exception applies only to old, unmodifiable variants requesting SMS or Call Log data; other ineligible variants must be deactivated. After rollout, extended review can take several weeks; an unapproved permission blocks Publishing API release, and initial/new-permission declarations must use the Console UI. See the [Permissions Declaration topic](../permissions-declaration/permissions-declaration.en-US.md) for the article's 14 body-link audit. This workflow guide does not decide AccessibilityService eligibility or expose account-specific form state. The sign-in declaration route, Help actions, and 12-item permissions sidebar are tracked separately. For ordinary app accessibility, use standard Android/Compose accessibility APIs; do not expand AccessibilityService's data or control surface merely for automation convenience.

This Help article still shows the 2021 Android 12 / target API 31 declaration start date. That is historical guidance, not the current Android-version trigger. Determine current obligations from the [current consolidated Sensitive Permissions policy](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en), the live Play Console declaration, and account notices. ### Remediation review sequence

1. Inventory every `addJavascriptInterface`, runtime-loaded script, WebView navigation, and iframe source in the app and its SDKs; determine which content the developer actually controls.
2. Do not inject a bridge into untrusted content. If reusing a WebView, control navigation in app code, remove the interface, and ensure the new page is reloaded before untrusted content runs. Prefer evaluating `addWebMessageListener` with an origin allowlist.
3. Do not expose SMS, accessibility, or other sensitive permissions/APIs through page scripts. Move any still-needed capability into app code and apply User Data disclosure and consent rules.
4. Check the exact affected packages and dates in Console/email, submit the repaired version, and track the review result.

These checks synthesize the Play remediation notice and Android implementation references. The account notice, device WebView version, redirects, and child-frame behavior still need verification in the target app.

### Android backup security best practices (platform guidance, not Play policy)

On October 24, reviewed [Security recommendations for backups](https://developer.android.com/privacy-and-security/risks/backup-best-practices), which states that it was updated October 25, 2024. Android recommends the Standard Android Backup system. Cloud backups are encrypted in transit and at rest; on Android 9+ with a device lock screen, backups can also use an end-to-end encryption key unknown to Google. Exclude particularly sensitive data, or require end-to-end encryption when it cannot be excluded.

- On Android 11/API 30 and lower, `requireFlags="clientSideEncryption"` can restrict sensitive backup data.
- On Android 12/API 31+, use `data-extraction-rules` with separate `<cloud-backup>` and `<device-transfer>` rules. The cloud section can set `disableIfNoEncryptionCapabilities="true"`; this blocks cloud backup when encryption is unavailable but does not disable D2D transfer, which is not sent to a server.
- Even if the app targets API 31+, provide the older `fullBackupContent` rules for Android 11 and lower. If `<device-transfer>` is omitted, D2D remains enabled for app data by default except cache and no-backup directories. Adding `<include>` changes the default from include-all to only the listed paths; `<exclude>` takes precedence.
- If implementing a custom export or nonstandard backup, secure the copy, restrict access by other apps, exclude data that should not migrate, and test regularly. These approaches are more error-prone. Auto Backup also recommends excluding device-specific identifiers and debug files, and the cloud quota is 25 MB per app user.

Auto Backup also documents cross-platform data migration to iOS starting with Android 16 QPR2 (API 36.1). Configure `<cross-platform-transfer platform="ios">` and provide `bundleId`, `teamId`, and `contentVersion`; a custom `BackupAgent` can identify the transfer with `FLAG_CROSS_PLATFORM_TRANSFER_IOS` and the new restore callback. This is Android data-transfer functionality, not a Google Play policy requirement.

## `QUERY_ALL_PACKAGES`: Play eligibility and Android package-visibility alternatives

[Google Play's broad package-visibility policy](https://support.google.com/googleplay/android-developer/answer/10158779?hl=en) applies to apps targeting API 30+ on Android 11/API 30+ devices. The installed-app inventory is personal and sensitive data. Eligibility is limited to cases where discovering all installed apps is required for a clearly promoted core feature and narrower visibility cannot support that feature. Declarations must explain the core use and be updated when use changes. An ineligible or undeclared use may lead to removal; deceptive or undeclared uses can lead to suspension or account termination.

Play lists device search, antivirus, file managers, and browsers as potentially eligible uses. Temporary exceptions may apply to core real-money gambling that needs app discovery for geofencing regulations, or security for regulated financial transactions; **the exception does not cover personal loans, credit lines, or apps facilitating access to personal loans**. The Financial Services policy separately prohibits `QUERY_ALL_PACKAGES` in covered personal-loan, credit/loan-facilitation, accessory-loan-tool, and EWA apps. Do not sell app inventories or collect/share them for ads or analytics monetization. Non-core P2P sharing and tasks achievable through narrower visibility are also ineligible.

Starting with Android 11, apps targeting API 30+ see a filtered app inventory by default. A limited set of apps is automatically visible, and the exact system-package set varies by device. **Starting another app's Activity usually does not require querying whether the app is visible first**: invoke the Intent and handle `ActivityNotFoundException`. Use manifest `<queries>` only when the UI needs to know whether a target exists in advance. Declarations can identify package names, Intent signatures, or Content Provider authorities; libraries can supply needs in an AAR manifest. `QUERY_ALL_PACKAGES` is a rare fallback, and Android capability does not equal Play approval.

### Android API and VPN implementation guide

The Android [`VpnService` API](https://developer.android.com/reference/android/net/VpnService) and [VPN development guide](https://developer.android.com/develop/connectivity/vpn) describe the system flow: request user approval with `VpnService.prepare()`, configure and establish a TUN interface with `Builder`, and call `VpnService.protect()` so the tunnel socket does not re-enter the app's own VPN and create a loop. Close the file descriptor and tunnel when `onRevoke()` is called. The service must be protected by `BIND_VPN_SERVICE` and declare the `android.net.VpnService` intent filter. The guide requires strong encryption for traffic between the device and VPN gateway. Start/stop controls, a non-dismissible notification while active, and Android's status indicators help users identify and control the connection. Only one VPN service can run for a user or work profile at a time; on Android 8.0+, a background-started VPN service must promptly move to the foreground.
